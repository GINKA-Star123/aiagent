# 后端与 Agent 一面：详细问答题库

本题库是[主面试指南](F:/aiagent/docs/interview/china-commerce-ads-backend-first-round-guide.md)的扩展，面向 Go/Python 后端与 Agent 场景。时间信息已按用户反馈标记为修正，本文不再围绕旧时间笔误设计追问。

以下 40 题不是团队内部题目，也不代表实际面试范围。每题提供可展开的答案，不建议整段背诵。练习顺序是“先用一分钟回答，再接受一到两个追问”。“设计建议”不能当成你的项目既有功能。

## 一、Go 与 Python：Q01–Q10

### Q01：Goroutine 为什么轻？开一万个就一定比一百个快吗？

**详细答案**

Goroutine 的创建与调度由 Go 运行时管理，其栈可以按需增长，通常比直接创建大量操作系统线程更轻。理解 GMP 时，G 是待执行的 goroutine，M 对应执行线程，P 持有执行 Go 代码所需的运行时资源。GOMAXPROCS 约束可并行运行 Go 代码的 P 数量，不是 goroutine 数量上限，也不是进程线程数上限。

并发数不是越大越好。如果任务等待网络，适度并发可以重叠等待；如果下游只有 50 个连接或已达限额，再开一万个只会增加排队、内存和超时。CPU 密集型任务的有效并行也受核心数和调度开销限制。

工程上应给并发、排队、连接和总截止时间设置预算，观察吞吐、P99 和资源利用率。用有界工作池或信号量控制执行中的任务数，而不是每来一个请求就不受控地派生 goroutine。

**追问：GOMAXPROCS=1 还能处理多个请求吗？**

能并发处理，并在等待与调度中切换，但通常不能在多个 P 上同时执行 Go 代码。并发描述任务交替推进，并行描述同时执行，二者不能混用。

**项目连接**：并行执行 DAG 分支时，瓶颈往往是 Provider 限额、连接池和预算，而不是“能创建多少 goroutine”。

### Q02：Channel 和 Mutex 怎样选择？Channel 为什么仍可能导致数据竞争？

**详细答案**

Mutex 适合保护共享内存的短临界区，例如更新缓存、计数器和执行上下文。Channel 适合表达任务流、事件流或所有权移交，例如工作池接收待执行节点、一个调度者汇总多个执行结果。二者不是优劣关系，而是模型不同。

通过 channel 发送一个指针，只是把指针值传给对方，不会自动深复制对象，也不会自动禁止发送方继续修改。若双方随后同时写该对象，仍可能存在数据竞争。应约定发送后不再修改、复制不可变数据，或继续用锁保护。

还要明确谁关闭 channel。通常由发送方或集中协调者在确认全部发送结束后关闭。接收方因为“暂时没有数据”就关闭，可能让其他发送者 panic。

**追问：有缓冲 Channel 就不会阻塞吗？**

不是。缓冲满时发送仍阻塞，缓冲空时接收仍阻塞；缓冲只是改变可暂存任务数。无界缓冲还会掩盖下游处理不过来的问题，所以背压应显式设计。

**易错点**：不要说“加了 channel 就没有共享内存问题”，也不要把关闭 channel 当成强制终止所有工作者。

### Q03：Context 超时后，任务真的停了吗？

**详细答案**

Context 提供取消信号和截止时间。调用 cancel 或截止时间到达后，Done channel 会关闭，使用者需要主动监听，并向 HTTP、数据库等支持 Context 的 API 传递同一个请求上下文。它不是强杀机制，不会中断任意正在运行的函数。

因此应该把截止时间贯穿调用链，而不是每层各给完整的 30 秒，导致端到端超过预算。创建派生 Context 后及时 cancel，释放相关资源。业务函数中的循环、阻塞发送和资源获取都要有退出路径。

客户端取消意味着调用方不再需要结果，但远端是否停止、是否已经产生业务效果，要看具体协议。已经提交的扣款不会因 Context 取消自动回滚。

**追问：父 Context 被取消，子 Context 会怎样？子取消影响父吗？**

父取消会传播给派生子 Context，子取消通常不反向取消父。多个分支共享父请求时，可以分别设置更短的子预算，但整体仍受父截止时间约束。

**项目连接**：SSE 客户端断开要关闭上游流；对工具调用还要追踪未知结果，而不是把“请求取消”理解为“操作肯定没执行”。

### Q04：什么是 Go 数据竞争？Race detector 没报错就一定安全吗？

**详细答案**

当多个 goroutine 访问同一内存位置，至少有一次写，并且缺少适当同步时，就可能存在数据竞争。锁、channel 和原子操作可以建立特定的同步关系，但它们是否保护了完整业务不变量，需要另外分析。

`go test -race` 是动态检测，只能观察测试实际执行到的行为，未覆盖的时序不能自动验证。即使完全没有数据竞争，也可能发生逻辑错误：例如两个 goroutine 分别在锁内读取余额，锁外做业务判断，再分别在锁内写入，单次内存访问都受保护，但检查与更新没有组成原子操作。

跨进程问题更不在 Go 内存竞争检测范围内，必须使用数据库约束、事务或共享协调机制验证。

**追问：计数器用 atomic 就够吗？**

如果业务只是单个计数值的原子加减，可能足够。若同时维护余额、状态、版本等多个字段，单字段原子不能自动保证它们的组合不变量，需要更高层同步或条件事务。

### Q05：Slice append 后为什么有时影响原切片，有时不影响？

**详细答案**

Slice 可以理解为底层数组、长度、容量的视图。复制 slice 变量并不会复制底层数组，因此两个 slice 可能共享元素。append 在剩余容量足够时可能复用底层数组，否则会分配新的存储并复制元素。

因此，判断“是否影响原对象”不能只看是否调用 append，而应看写的位置与是否共享数组。若需要独立数据，显式复制。一个很小的子 slice 还可能保持对巨大底层数组的引用，使其无法回收。

**追问：`s[:len(s):len(s)]` 能解决什么？**

三索引切片把可见容量限制为长度，后续 append 需要新分配时可避免覆盖共享尾部。但它没有复制已有元素，直接修改已有下标仍会影响共享数组；它也不能作为释放原大数组引用的通用替代。

**口述小例子**：先画底层数组，再画两组 len/cap，最后标记 append 的写入位置，比背扩容倍率更可靠。

### Q06：为什么返回 error 后 `err != nil`，但里面的指针是 nil？

**详细答案**

接口值不仅包含值，还包含动态类型。一个 `*MyError` 的 nil 指针放入 error 接口后，动态类型仍存在，因此接口整体不是 nil。常见问题是函数声明返回 error，实际返回一个已声明但未赋值的 `*MyError`。

成功时应直接返回 nil。包装错误时用 `%w` 保留错误链，调用方用 `errors.Is` 判断特定哨兵错误，或用 `errors.As` 找出具体错误类型。字符串比较不稳定，因为上下文和包装会改变文字。

**追问：所有错误都包装成一个“内部错误”行不行？**

面向用户可以隐藏敏感内部信息，但服务内部应保留分类、原因和关联 ID。否则调用者无法区分不可重试的参数/授权错误与可恢复的网络故障，监控也无法定位。

**项目连接**：共享状态的归属冲突不能被统一包装成普通可降级异常，否则可能绕过用户边界。

### Q07：Defer、panic、recover 的边界是什么？

**详细答案**

Defer 在函数退出时执行，顺序是后进先出；注册时参数通常已经求值。它适合关闭文件、释放锁、结束 trace 等资源清理。循环内大量 defer 不会每轮自动执行，而是积累到外层函数返回，应注意资源持有时长。

Panic 表示异常控制流，会沿当前 goroutine 的调用栈展开并执行 defer。Recover 必须在同一 goroutine 中合适的 defer 调用位置生效，不能在主 goroutine 里捕获其他 goroutine 的 panic。

不应把所有业务失败都设计成 panic，也不应 recover 后装作操作成功。中间件可恢复请求级 panic 并记录必要日志，但必须返回失败并确认资源、事务和状态是否已清理。

**追问：defer 能修改返回值吗？**

可以影响命名返回值，但匿名返回值和求值顺序要分别看。面试时逐步走“计算返回表达式、赋值返回变量、执行 defer、实际返回”，不要靠直觉猜。

### Q08：Go GC 和逃逸分析需要掌握到什么程度？

**详细答案**

逃逸分析是编译器决定对象能否放在栈等位置的一部分分析，不是“写 new 就一定在堆”。对象是否被返回、是否跨作用域持有、接口与闭包使用方式等会影响结果，具体要看编译器版本和优化。

GC 负责回收不再可达的对象。常见 Go 实现具有并发标记清扫等机制，但仍可能存在暂停和 CPU 成本。分配速率高、长期持有大对象、无界缓存，都可能让 GC 和内存压力增加。

优化时先看 pprof 与分配热点，缩短对象生命周期、去掉不必要复制与无界持有，再考虑对象池。sync.Pool 不是持久缓存，对象可能被回收，也不保证下一次取到之前放入的那个对象。

**追问：内存一直高就一定是泄漏吗？**

不一定。运行时保留、缓存或短期峰值都可能使 RSS 不立即下降。要看堆对象可达性、增长趋势、GC 后存活量和业务负载，不能只看一次系统内存截图。

### Q09：FastAPI 用了 async，为什么一个慢请求拖慢其他请求？

**详细答案**

async 路由运行在事件循环中。若直接调用同步网络 SDK、time.sleep 或长时间 CPU 计算，事件循环就无法及时调度其他协程。async 只是声明协程，不会自动把同步操作变成可等待操作。

异步兼容的 HTTP/数据库客户端可以在 I/O 等待时让出执行；同步 I/O 可以通过受控线程池或 asyncio.to_thread 包装；大量纯 Python CPU 计算通常应考虑进程或独立服务。FastAPI 的普通同步路由一般由框架在线程池执行，但 async 路由内部直接调用的普通函数不会因此自动被转移。

还要观察线程池是否饱和。无限把任务丢给线程池也会产生排队和内存压力，单纯加线程并不等于解决问题。

**追问：wait_for 超时后线程会停止吗？**

通常不会。等待线程结果的协程取消，不代表操作系统线程里的同步调用被强制中断。应同时配置 SDK/Socket 超时，确保请求结束后资源回收，并为可能继续完成的业务动作设计幂等和状态核验。

### Q10：GIL 会不会让 Python 多线程完全没有意义？

**详细答案**

不能这样概括。常见带 GIL 的 CPython 构建通常一次只有一个线程执行 Python 字节码，但阻塞 I/O 和部分 C 扩展可以释放 GIL，因此多线程仍可能改善 I/O 密集型任务的吞吐。某些原生计算库也有自己的并行机制；其他 Python 实现或构建的条件不同。

对于纯 Python CPU 密集循环，增加线程通常不能获得相应的多核加速。可以使用多进程，但要承担序列化、内存和进程通信成本。异步方案则主要提高大量等待型任务的资源效率，不是把 CPU 计算变快。

GIL 不应被当成业务锁。读改写、跨对象检查更新以及 I/O 前后的状态变化都可能需要同步。多 Uvicorn Worker 还拥有独立内存，不能依赖进程内字典共享会话。

**追问：为什么不把所有请求都交给多进程？**

模型调用通常是外部等待，进程开销未必值得；同时模型实例、缓存和连接会被复制。应按 CPU、I/O、内存及取消语义选择，不以语言标签决定架构。

## 二、数据库与业务状态：Q11–Q16

### Q11：给订单查询设计索引，你会怎么做？

**详细答案**

先确认主要查询：按什么过滤、如何排序、取多少行、数据分布和更新频率。例如用户订单页的条件是 user_id，按 created_at、id 倒序分页，那么 `(user_id, created_at DESC, id DESC)` 是值得验证的候选，而不是立刻给每个字段都建索引。

B+ 树类索引通过页组织与较小树高支持定位和范围扫描；联合索引的列顺序应与查询形态对应。但最终是否使用、是否有效，要看执行计划、选择性、回表、排序和统计信息。小表或大量行命中的查询可能顺序扫描更合适。

索引会增加写放大、存储和维护成本。覆盖读取也受数据库机制影响，例如 PostgreSQL 的 index-only scan 还与可见性等条件有关，不能声称“选的列全在索引里就绝不访问表”。

**追问：为什么 `LIKE '%keyword%'` 普通 B-tree 往往帮不上？**

前缀不确定时难以形成连续可定位的键范围。可按数据库能力考虑全文检索、trigram 等专门索引，或者改查询需求，不能简单让所有模糊搜索走普通联合索引。

### Q12：MVCC、隔离级别和幻读应该怎样连起来讲？

**详细答案**

MVCC 通过多版本和可见性规则，让读操作看到特定快照，减少普通读写互相阻塞。它是一种实现机制，隔离级别则是对事务能观察到哪些并发现象的语义约束，两者不是同一个词。

PostgreSQL 默认 Read Committed，通常每条语句获取自己的可见快照，所以同一事务两次查询可能看到其他事务新提交的数据。Repeatable Read 为事务提供稳定快照，但快照隔离仍可能产生写偏差：两个事务读取相同条件，各自更新不同记录，最终共同破坏业务不变量。

Serializable 提供更强的串行化语义，但事务可能因序列化冲突失败，应用需要正确重试。不能把 MySQL 默认隔离级别、间隙锁等细节原样套到 PostgreSQL。

**追问：库存只有 1，MVCC 能防超卖吗？**

不能只靠“启用 MVCC”。应使用原子的条件扣减、行锁或明确的版本控制，并检查影响行数。读到余额再无条件覆盖会失去并发更新，业务约束必须体现在写入条件或事务锁定中。

### Q13：审核通过要创建企业并更新申请，怎么保证原子性？

**详细答案**

若两项写入属于同一数据库中的一个业务事务，应放到同一个事务里：读取并校验申请状态，创建或关联企业记录，更新审核状态，写必要审计，最后提交。任一步失败应回滚，不能企业已经存在但申请仍显示待审核。

使用 ORM 时，所有仓储写操作必须使用事务对象 tx。若某个仓储方法仍引用全局 db，就可能脱离事务。还需要唯一约束，避免重试创建重复企业。

如果审批后还要发消息，数据库与消息系统不天然共享一个事务。可以在事务内写 outbox 记录，提交后由可靠发送器发布，消费者按事件 ID 幂等。这个设计实现的是有约束的最终传播，不是无需重试的魔法原子提交。

**追问：可以事务里先调用模型审核再写库吗？**

不建议长事务跨慢网络等待。可以先做模型建议或人工审核，再用短事务检查当前版本并提交；如果状态已经改变，就重新确认，而不是持锁几十秒等待模型。

**项目边界**：低空平台已查代码中的分步写入不能直接宣称已有完整事务。此处是你应能分析并提出的改进方案。

### Q14：两个请求同时扣库存或修改预算，用乐观锁还是悲观锁？

**详细答案**

先明确业务不变量。例如库存不得小于零，可以在数据库中做 `UPDATE ... SET stock=stock-qty WHERE id=? AND stock>=qty`，以影响行数判断是否成功。这样检查与修改属于同一原子写，不需要先把库存读出来再计算。

乐观版本控制适合冲突相对可控、可以失败重试的更新：WHERE 同时匹配 version，成功后递增版本。悲观行锁适合需要读取多个值并协调更新的场景，但必须控制锁顺序和持有时间。高竞争下无界乐观重试同样会放大负载。

不论使用哪种锁，重复请求的业务幂等仍需独立处理。相同请求重试不能再扣一次；不同合法请求则应各自扣减。

**追问：数据库扣成功，但响应丢了怎么办？**

调用方应带同一幂等键重试或查询已有结果。服务端持久化该键对应的操作和结果，不能因客户端没收到就把操作当作没发生。

### Q15：一个 SQL 很慢，你第一步做什么？

**详细答案**

先确认慢发生在连接池等待、锁等待、SQL 执行、结果传输还是应用处理，而不是立即加索引。收集具体 SQL、参数分布、频次、执行时间与最近变更，核对是否仅某租户或大数据量场景出现。

再看执行计划：估算行数与实际行数差异、扫描方式、过滤、排序、连接顺序、临时落盘等。估算不准可能是统计信息或数据倾斜，索引缺失只是可能原因之一。ORM 的 N+1 也可能让单条 SQL 很快但整个请求很慢。

EXPLAIN ANALYZE 会真实执行语句；线上写语句不能不加防护地拿来测试。优化后应在相近负载和数据上比较 P95/P99、数据库资源、锁和写入成本。

**追问：SQL 不慢但请求还是慢？**

检查连接获取、外部调用、串行 N 次小查询、网络回传和序列化，以及其他线程/协程是否阻塞。一次日志里的 SQL 时间不覆盖整个请求生命周期。

### Q16：为什么深分页慢？游标分页有什么代价？

**详细答案**

大 offset 需要扫描或跳过前面大量行，即使只返回十条，也可能做很多无效工作。Keyset 分页利用上次最后一条的排序键继续检索，例如按 created_at DESC、id DESC，从小于上个游标的键开始取。

排序必须稳定，created_at 相同时增加唯一 id 作为 tie-breaker。查询条件与索引要匹配，游标也应绑定过滤条件和排序版本，必要时签名，避免客户端随意构造越界条件。

代价是很难直接跳到“第 1000 页”，总页数也不一定低成本可得。并发插入和删除时，游标分页往往比 offset 更稳定，但仍需定义一致性快照、是否允许看到新数据、是否保证完整遍历。

**追问：排序字段更新怎么办？**

记录可能移动到游标前后，产生漏读或重复。可选择不可变排序键、快照时间边界或接受弱一致并在客户端去重，不能笼统说游标分页绝不重复。

## 三、Redis、队列与可靠性：Q17–Q23

### Q17：把 Redis 分布式锁从加锁讲到故障边界。

**详细答案**

基础实现是使用一个命令设置带唯一持有者 token 和到期时间的键，例如 SET key token NX PX ttl。NX 保证键不存在时才能获取，TTL 避免进程崩溃后永远不释放。释放时用 Lua 原子地“比较 token 后删除”，防止旧请求误删新持有者的锁。

但 token 解锁只解决误删，不解决过期后旧请求继续写。请求 A 暂停，锁过期，B 获取并完成写入，A 恢复后仍可能覆盖结果。可以设计续约并处理失效，或用递增 fencing token，让受保护存储拒绝旧代次；关键是所有相关写路径都执行正确校验。

Redis 的主从切换、网络分区和持久化策略也影响保证。高风险资金或订单约束不能只依赖一把锁，应由数据库状态机、唯一约束和幂等共同保护。

**追问：续约成功就绝对安全了吗？**

不是。续约线程也可能暂停或失败，客户端对是否仍持有锁可能没有及时感知。失去锁时必须停止受保护动作或依赖资源端拒绝陈旧写，不能只打印一条告警继续提交。

### Q18：更新数据库后删缓存，为什么还会不一致？

**详细答案**

“先更新数据库，再删除缓存”是常见 cache-aside 策略，但不是严格一致证明。删除可能失败；并发读可能在数据库更新前读取旧值，却在删除后才把旧值写回缓存；主从延迟还可能让回源读到旧数据。

处理方案取决于容忍度：缓存短 TTL 提供最终自愈，失败删除进入可靠重试，写入或失效事件通过消息/CDC 传播；对于特定关键数据，可用版本号防旧值回填、统一读主库或不缓存关键决策结果。每种方案都有复杂度与性能成本。

延迟双删只能覆盖某些时间窗口，不能在任意调度、任意延迟下证明强一致。越强调一致性，越要说清读写边界和真实故障模型。

**追问：订单是否支付能不能只读缓存？**

展示可以接受短时旧值，但是否允许退款、发货等关键决策应由权威状态和条件迁移判断，不把缓存展示状态当最终业务事实。

### Q19：Redis 的 TTL、淘汰与持久化有什么区别？

**详细答案**

TTL 描述某键何时应过期；实际删除可涉及惰性和周期检查等机制。内存淘汰是在内存达到阈值时按策略移除键，不要求键已经到期。持久化则描述如何把状态保存到磁盘，以便重启恢复。

RDB 快照和 AOF 的丢失窗口、恢复时间和写入开销不同。即使 Redis 有持久化，也不能直接等同于“不会丢”。如果 Redis 同时承载缓存、任务和执行状态，它们的丢失后果不同，应考虑实例隔离、资源配额或至少明确策略，避免缓存压力淘汰关键会话或锁相关键。

**追问：到期时间能保证业务记录准时消失吗？**

不能把物理删除时刻当定时业务事件。业务应在读取和提交时判断有效期，定时任务与删除审计需要独立机制；同时处理索引键与数据键过期不同步的情况。

### Q20：给模型接口做限流，为什么只限制 QPS 不够？

**详细答案**

模型请求执行时间长，低 QPS 也可能积累很高并发。还要限制在途请求、队列长度、每租户 Token、总费用和 Provider 配额。长输出与短输出占用资源差异大，单纯请求数并不反映成本。

令牌桶可以允许受控突发，固定窗口简单但有边界突刺；全局限流需要跨实例原子计数或专门服务。入口限流之外，还要防内部重试绕过预算和大量租户共同挤占下游。

拒绝时返回可理解的状态和重试信息。排队应有上限和截止时间，不能为了提高成功率无限排队。针对安全敏感操作与普通聊天，依赖不可用时的 fail-open/fail-closed 策略也应不同。

**追问：怎么估算并发需求？**

稳定条件下可以用 Little 定律 L≈λW 理解平均在途量，但要保证统计边界一致，并考虑尾延迟和突发。它是容量推理工具，不代替真实压测。

### Q21：幂等接口到底怎么设计？

**详细答案**

幂等要求同一个业务意图被重复请求时，不重复产生预期副作用。通常由调用方提供稳定幂等键，服务端将键与主体、操作类型、请求摘要和结果绑定，并通过数据库唯一约束原子创建操作记录。

状态可以是处理中、成功、失败或结果未知；重复调用需要按状态返回已有结果、等待或引导查询。相同 key 但不同请求内容必须拒绝，而不是意外复用旧结果。键的保留时间应覆盖合理重试窗口，资金类场景往往需要更持久的业务唯一约束。

对外部系统的副作用还应使用其幂等接口；如果外部执行成功而本地写结果失败，靠幂等查询和对账恢复，不声称一个本地事务能自动包住远端执行。

**追问：接口被同时重试十次怎么办？**

用唯一约束选出唯一创建者，其他请求查询同一操作记录；处理中状态要有超时与恢复机制。进程内锁只能降低单实例竞争，不能当最终去重依据。

### Q22：消息至少一次投递是什么意思？如何避免重复消费？

**详细答案**

至少一次意味着在系统约定的可靠性条件内，消息可能被再次投递，因此消费者必须考虑重复。只有业务处理成功后才确认可以减少丢失，但“写库成功、确认前崩溃”仍会导致重投。

若业务数据与去重记录在同一数据库，可以把消息 ID 去重、业务状态迁移和结果写入放入同一事务；重复消息命中唯一约束时读取已处理结果。若调用外部接口，则需要业务幂等键，而不是只在本地写一个“消费成功”。

失败处理应有退避、重试次数、死信和人工修复路径。还要按业务定义顺序：同一个订单可以按版本或状态机拒绝旧事件，但不能假设所有分区和消费者天然全局有序。

**追问：死信队列代表问题解决了吗？**

不是，只是隔离无法自动处理的消息。必须有可观测性、告警、原因分析和安全重放机制；重放仍需幂等与权限。

### Q23：重试、超时、熔断、降级怎样配合？

**详细答案**

超时限制等待上限；重试处理部分临时失败；熔断阻止持续攻击已经不健康的下游；降级用受约束的替代能力继续服务。四者的目的不同，不能全靠“多试几次”。

先分配端到端截止时间，再分每次调用预算。只对明确可恢复的错误重试，使用退避和抖动，尊重 Retry-After，避免 SDK 和业务各重试三次导致九次调用。请求可能已经产生副作用时，应查询或使用幂等协议，不做盲重试。

降级必须保持语义诚实：没有查到知识就不生成虚假引用，TTS 失败可返回文字，共享归属检查失败不能当无权限限制继续。熔断恢复要有探测与半开策略，不能永久放弃依赖。

**追问：流式输出已经发出一半能重试吗？**

通常不能在无协议支持下透明重放，因为会重复文字、工具动作或计费。要么有明确接续、事件序号和去重语义，要么返回可见的失败终态，让用户选择重新发起。

## 四、网络、安全与工程：Q24–Q28

### Q24：把一个生产可用的 SSE 链路讲完整。

**详细答案**

SSE 使用 HTTP 响应传递事件，data 行承载内容，事件以空行分隔，event/id 等字段可以表示类型与标识。服务端设置正确 Content-Type，及时 flush；代理层要考虑缓冲、空闲超时与连接限制。

链路开始前先完成认证、权限和参数校验，避免已经返回 200 后才发现请求根本无效。开始之后如果 Provider 失败，应发送 error 终态并关闭，客户端以终态而不只是 HTTP 状态判断结果。Provider 的文本、工具参数片段与 usage 事件需要分类型，不要求每个事件恰好一个 token。

客户端断开应取消 Go/Python 上游并清理流，但远端计费终止仍依赖 Provider 协议。慢客户端需要背压和有界队列；心跳可以维持空闲链路，却不能掩盖上游已经死亡。

**追问：有 event id 就能恢复吗？**

不能。服务端还需要持久化/缓冲可重放事件、按 Last-Event-ID 或自定义游标定位，并定义保留期、重复处理和已发生工具动作的语义。浏览器能自动重连不代表模型能从断点继续生成。

### Q25：JWT、RBAC、租户隔离三者怎么分工？

**详细答案**

JWT 是一种携带声明的 token 形式。认证需要正确校验签名、允许算法、有效期及 issuer/audience 等约束，并考虑密钥轮换和撤销策略。JWT 默认并不加密，不能随便放敏感内容。

RBAC 根据用户角色决定允许的动作，但用户属于管理员角色，并不自动有所有 Workspace 的权限。资源授权还要检查租户、成员关系和对象归属，且 user_id 等主体信息应来自可信认证上下文，而不是客户端随便传入的字段。

检索、下载、历史记录、任务状态查询和工具调用都应贯彻相同边界。只在创建时查权限，后续按 run_id 查询不再过滤，是常见越权路径。

**追问：用户退出后旧 JWT 还有效怎么办？**

可采用短期 access token、可撤销 refresh token、服务端版本/会话校验或 denylist。每种方案在无状态程度、实时撤销和存储成本之间有取舍，不能既宣称完全无状态又承诺任意 token 立即全局撤销而无额外机制。

### Q26：HTTPS、CORS 和 CSRF 分别解决什么？

**详细答案**

HTTPS 依靠 TLS 保护传输机密性、完整性与服务器身份校验，不解决服务端的对象越权。CORS 是浏览器跨源访问响应的策略控制，不是身份认证；非浏览器客户端不受它同样约束。

CSRF 关注浏览器自动携带凭据时，其他站点诱导用户发起有副作用请求的风险。可用 SameSite Cookie、CSRF token、Origin/Referer 检查和安全方法约束等组合防护。若使用 Authorization Bearer token，风险模型不同，但 XSS 窃取 token 等问题仍存在。

生产配置应按身份方式设计，不机械认为“允许所有 Origin”或“禁用 Cookie”能解决全部问题。带凭据的跨源访问还有浏览器特定规则，需按实际部署验证。

**追问：有 HTTPS 就不用脱敏日志了吗？**

当然不是。TLS 只保护传输路径，服务端日志、监控、数据库和第三方模型请求依然可能暴露敏感信息，必须按数据最小化原则处理。

### Q27：日志、指标、Trace 有什么区别？

**详细答案**

日志用于记录离散事件和上下文；指标用于低成本聚合趋势、分位数和告警；Trace 用于还原单个请求跨服务的阶段与依赖关系。它们互补：P99 升高由指标发现，定位到哪条路径靠 trace，解释具体失败原因靠日志。

跨 Go 和 Python 需要传播 trace context/request_id，并区分业务 run_id、会话 ID 与观测 ID。不能把用户 ID 或每个请求 ID 都作为高基数指标标签，否则监控成本会失控。多 Worker 下，进程内统计不自动构成全局指标，需要按指标类型正确聚合。

延迟必须定义起止点：排队、网络、Provider、首 token 和总完成时间是不同量。平均各 Worker 的 P99 通常不能得到全局 P99；应基于直方图等可合并统计或原始观测计算。

**追问：应该记录完整 Prompt 方便排错吗？**

默认不应无约束记录。可以记录摘要、长度、模板版本、证据 ID 和脱敏失败码，必要的原始数据采样要遵循授权、保留期和访问控制。可观测性不能成为隐私泄露通道。

### Q28：Mock、单元测试、契约测试和集成测试分别证明什么？

**详细答案**

单元测试验证局部规则和边界；契约测试验证输入输出、状态码与错误形态；smoke 验证核心链路能跑通；真实依赖集成测试验证数据库、Redis、模型 SDK 等连接与协议。Mock 提供确定性、速度和离线能力，但会把被替代部分的真实行为排除在证明之外。

例如 Mock 聊天成功不能证明模型答对，伪造 Redis 通过不能证明真实 Lua、TTL 与故障时序正确。反过来，真实模型跑通一次也不能替代边界单测和长期回归。

可复现 CI 应锁依赖、固定必要配置、使用合成 fixture、隔离本机缓存和未入库资源；真实依赖测试按标记与环境明确执行或跳过，不偷偷联网下载模型后声称离线成功。

**追问：测试很多就意味着质量高吗？**

数量只是规模信息。更重要的是断言、故障路径、隔离、可复现性和是否覆盖业务风险。要能解释某次回归以前为什么会漏、补了什么测试，以及测试不能证明什么。

## 五、Agent 与工作流：Q29–Q35

### Q29：设计一个 DAG 执行器，需要哪些数据与状态？

**详细答案**

定义层要有版本化 Schema、节点、边、参数和输入输出契约。校验层检查引用、配置、环和路径约束。执行层为每次运行保存 run_id、Schema 快照、输入、节点状态、输出、错误与时间，不把定义直接当运行状态修改。

串行版本可按拓扑序执行。并行版本需要 ready 队列、前驱完成计数、有界资源、线程安全结果存储及汇合语义。节点失败后，后继是 fail-fast、skip、fallback 还是补偿，必须是产品与执行模型明确规定的行为。

崩溃恢复不能只把“running 改回 pending”就完成。节点可能已经调用外部工具但没记录成功，重执行可能重复副作用，所以需要操作幂等键、结果核验和租约恢复规则。

**追问：为什么不能让 LLM 每次直接决定下一个节点？**

可以为受限场景设计动态路由，但决定权仍受允许节点、预算、权限与终止条件约束。对需要审计和稳定结果的流程，显式工作流往往更可控；不是越动态越高级。

### Q30：完整工具调用循环具体怎样走？

**详细答案**

应用提供工具名、说明与参数 Schema；模型输出 tool_call_id、工具名和参数。应用解析参数，检查工具是否允许、参数是否符合 Schema 和业务约束，再按可信调用者身份授权执行。结果以对应 tool_call_id 回填，模型才能把观察结果整合进回答，或在预算允许时提出下一步。

流式工具参数往往分片到达，不能每收到一个片段就执行，也不能只因 JSON 能解析就判定所有参数已经完整。处理多个调用时要明确依赖和是否允许并行，有副作用工具还要确认、幂等与审计。

循环由最大轮次、总截止时间、Token/费用、重复动作检测和最终回答等条件终止。工具文本是数据，不应提升为系统指令。真实执行、Mock 桥接与协议类型定义是三种不同完成程度。

**追问：工具名是白名单就够安全吗？**

不够。同一“查订单”工具也可能查询别人的订单；外部 URL 参数可能引起 SSRF；退款工具还需要金额、状态、角色和确认。安全边界应在工具适配器/业务服务里确定性执行，而不只写在 Prompt 中。

### Q31：混合检索和 RRF 怎样证明不是盲目拼接？

**详细答案**

BM25 利用词频、逆文档频率和长度因素，适合专名、编号与精确词；向量检索捕捉语义相似，适合同义表达。两路可能互补，也可能共同失败，所以要在真实问题集上比较单路与融合基线。

RRF 用排名倒数和融合不同尺度的结果：`Σ 1/(k+rank)`。同一 chunk 的标识必须稳定以去重，保留每路排名和来源便于解释。k 是平滑项；它不是输出数量，也不是置信概率。额外分数加成要看量级，不能让一项轻易淹没融合本身。

验证需要分类型看专名、别名、语义改写、多文档和无答案问题。还要看最终片段与注入行为，不能只报告文档级 hit 就说问答成功。检索器返回一些候选并不表示存在足够证据。

**追问：向量搜索近邻一定准确吗？**

近似搜索是速度、内存与召回的权衡，还受 Embedding 和过滤影响。即便拿到了数学意义上最近的向量，也不保证对应业务事实相关、最新或有权限。

### Q32：如何设计有说服力的 RAG 评测？

**详细答案**

先定义任务和判分对象：检索文档、证据片段、注入决策、最终答案可能需要不同标准。问题集按真实错误类型分层，包含负例、歧义、专名、多源与多轮；每条有可追溯的语料和期望，不通过反复改期望来追指标。

实验固定语料指纹、问题集版本、模型/Embedding、Prompt、检索参数与判分规则。使用开发集调参，独立保留集评估；若多个因素一起改变，只能解释为组合对照，不能把全部收益归因某一项。模型生成可多次运行，但同一问题的多次输出不是独立的新问题。

规则判分可复现，但词命中不等于语义正确；LLM Judge 更灵活，却有误判和偏差。因此应结合人工复核、失败案例与成本/延迟，而不是只报单一通过率。20 条实验必须承认样本小，不与后续不同数据集直接比较。

**追问：Judge 自己会错怎么办？**

做一组人工标注校准样本，检查 Judge 的漏判与误判；固定评分维度、盲化实验版本、必要时交换答案顺序复核，记录分歧并人工仲裁。Judge 不是绝对真值，尤其不能让被评答案中的指令影响评分。

### Q33：长期记忆怎样避免越记越乱？

**详细答案**

先定义值得记什么：稳定偏好、用户明确要求保留的事实与长期目标，而不是把每轮原文都写入。写前经过敏感过滤和策略判断，记录主体、来源、时间、类型及必要版本。语义相似只能提供合并候选，不能直接证明两条事实相同。

冲突要区分“用户偏好更新”“事实不一致”“不同作用域”。例如“喜欢咖啡”与“晚上不喝咖啡”并不必然冲突；“已经搬家”则可能使旧地址失效。用户显式更正和删除应具有明确优先级，避免后台抽取又把删除内容写回来。

召回后按相关性、有效期、置顶、可信来源和预算筛选。用户禁用长期记忆时，要明确定义是否停止读写，而不是只隐藏管理界面。清理要覆盖权威存储与派生索引，备份保留也不能随口承诺立即删除。

**追问：摘要是不是一定比历史更好？**

摘要节约上下文，但可能遗漏、失真或把不确定信息变成事实。应保留关键来源、校验实体与时间，必要时保留原文引用；摘要不是无损压缩。

### Q34：怎样防 Prompt Injection？为什么只写安全提示不够？

**详细答案**

输入可能来自用户、网页、文档、图片 OCR、工具结果或长期记忆，其中的指令不应自动升级为系统权限。Prompt 隔离与明确角色有帮助，但模型仍可能受误导，所以安全不能只依赖它正确理解文字边界。

防护重点在确定性执行层：最小权限工具、租户过滤、服务端授权、外部目标限制、输出校验、高风险动作确认和审计。敏感系统凭证不应放进可被模型回显的上下文；检索到的规则文本也不应改变工具权限。

测试需要包括文档里要求泄露密钥、工具返回要求转账、用户伪造管理员、跨租户检索等负例。要衡量攻击成功率和误拒绝，而不是只准备几个固定关键词规则。

**追问：把文档放在 XML 标签里就安全了吗？**

标签只能帮助表达数据边界，不提供强制隔离。真正安全保证仍来自模型无权直接操作、服务端每次独立校验，以及高风险动作的受控协议。

### Q35：模型成本和延迟怎么优化，而不是只说压缩 Prompt？

**详细答案**

先拆分总耗时：排队、网络、检索、多个模型阶段、首段输出和总生成。先确定哪个是主要瓶颈，避免优化几毫秒的序列化却增加一次几秒的模型调用。Token 也要分输入、输出、缓存命中及不同模型计费口径。

可选方案包括减少不必要的模型阶段、并行独立 I/O、限制输出、筛选和去重证据、摘要、按任务路由模型、缓存稳定可复用的检索或结果。每种方案都可能伤害质量或引入隐私问题，所以必须同步比较质量、P95/P99、费用、失败率和缓存隔离。

不能把缺失 usage 当零成本，也不能只报一次最快结果。Provider 价格会变化，费用估算要记录模型、时间、价格版本及不确定项。流式改善感知延迟，不自动降低计算成本。

**追问：什么时候不优化？**

没有量化瓶颈或优化会明显增加复杂度、损害质量时，可以保留现状并记录证据。能证明某项当前不值得做，也是一种合理的工程结论。

## 六、业务、排障与行为：Q36–Q40

### Q36：DDD 四层有什么意义？怎样避免过度设计？

**详细答案**

分层的价值是把业务规则、业务用例和技术实现的变化隔离开。接口层处理协议；应用层编排用例与事务；领域层表达业务概念和不变量；基础设施提供数据库、消息和外部服务。依赖应尽量朝稳定的业务抽象，而不是让领域直接依赖 HTTP 或具体 ORM。

但建立四个目录不代表完成了丰富领域模型。当前简单 CRUD 可以用清楚的服务层与仓储边界，没必要给每个字段创建复杂对象。只有当业务概念、生命周期或约束值得单独建模时，才增加聚合、值对象等抽象。

对于已有项目改造，应优先保持行为兼容并用契约测试锁住，再逐步迁移，不一次性改路由、模型和数据语义。自己项目若仍有规则集中在应用层，就准确称“DDD 风格分层”。

**追问：业务规则到底放应用层还是领域层？**

“安排谁先调用哪个服务”属于用例编排；“这个状态是否允许审核通过”是业务不变量，适合放在可复用领域行为中。现实项目可以循序渐进，关键是规则有唯一可靠的执行位置和测试，而不是机械看文件夹名字。

### Q37：广告数据分析为什么先问指标口径？

**详细答案**

同一个“转化率”可能是点击到下单、访问到支付或曝光到转化，分母不同结论完全不同。CTR 也可能按事件次数或去重曝光计算，CVR、ROAS 和 ROI 要分别定义。应明确统计主体、事件时间、去重键、归因模型、窗口、退款和延迟数据。

Join 事件时容易出现一对多放大，例如一条曝光有多次点击，再连接多个订单，计数和金额都会重复。应先按目标口径聚合和去重，再关联，并通过边界样例检查。

如果用 Agent 解读报表，应让工具返回明确的指标定义与时间范围，模型只解释数据，不能自行更换口径。对“提高预算”“暂停投放”这样的动作建议，也要与真实执行权限分开。

**追问：CTR 上升但收入下降可能吗？**

可能。点击质量下降、转化率下降、客单价或利润下降、流量结构变化、归因延迟等都可能发生。需要看漏斗和分群，不将单一中间指标等同于最终业务收益。

### Q38：线上接口突然变慢，给一个完整排查顺序。

**详细答案**

第一步界定影响：何时开始、哪些接口/租户/地区、是全量还是少量、错误率是否升高、是否刚发布。必要时先按预案回滚、限流或降级止损，而不是边猜边改多个参数。

第二步按链路拆解：入口排队、应用调度、连接池、DB、Redis、模型 Provider 和结果发送。观察 P95/P99、在途数、队列长度、CPU、内存、GC、锁等待和依赖错误。CPU 不高可能恰恰说明卡在 I/O 或等待资源。

第三步建立可验证假设，例如 Provider 延迟、数据库锁、线程池耗尽或新版本串行增加一次调用；用 trace、日志和单一变更验证。恢复后补回归与容量/故障测试，不能只以“重启后好了”结束。

**追问：没有 Trace 怎么办？**

先使用现有 request_id、分阶段耗时和依赖日志交叉定位，逐步加低风险采样。不应为了排错立刻全量打印敏感 Prompt，也不应在线上无审核执行破坏性压测。

### Q39：AI 帮你写项目，怎么证明能力是你的？

**详细答案**

如实说明使用范围：查资料、初稿、测试建议或局部实现。能力证明不是宣称“从没用 AI”，而是能解释需求、调用链、数据和错误边界，能发现不兼容依赖，能验证测试和修正错误，并对交付负责。

选择一个具体函数演示：输入从哪里来、哪些条件必须成立、调用外部依赖的失败类型、结果写到哪里、哪个测试证明边界。再讲一个生成代码并不正确的案例，例如空图库提前加载模型或平台相关排序导致指纹漂移。

不要假称所有代码都经过完整人工审查；没掌握的实现承认需要补课。也不要把故障归责给 AI 后停止分析，工具参与不改变开发者应做的验证。

**追问：现在不用 AI，能自己写吗？**

先选择一个范围明确的能力，现场给数据结构、步骤和边界，再独立完成。越能把复杂系统拆成小模块，越容易证明你不只是拼接生成结果。

### Q40：没有团队实习经验，怎么回答沟通、学习和困难？

**详细答案**

独立项目不能替代团队经历，但可以展示可靠的工作方式：遇到模糊需求先确认输入输出与验收，接口约定写清楚，风险及时同步，变更附测试和说明，没把握的结论明确标记。若有真实课程协作或团队项目，再具体讲如何分工与解决分歧，不虚构同事和线上事故。

讲困难用真实 STAR：原本问题是什么、你承担什么、如何提出假设与验证、结果如何、还有什么不足。失败故事也可以有价值，前提是你能解释下次如何避免同类问题，而不是只说“我很努力”。

学习能力要有证据：新技术解决了什么实际问题，查了哪些权威材料，做了什么最小实验，怎样知道自己理解错了。堆框架名不能证明快速学习。

**追问：和评审意见不同怎么办？**

先复述共同目标与对方担忧，基于约束比较方案，必要时做小实验或记录决策；如果团队已有明确规范，先遵守并提出有证据的改进。不把争论升级成人际输赢，也不在没理解的情况下表面接受。

## 七、把这 40 题练成自己的答案

每题按四轮练习：

1. 关闭答案，用 60 秒回答，暴露自己缺的机制。
2. 对照详细答案，只补三个关键点，不抄整段。
3. 加一个项目例子和一个反例，区分已实现与建议。
4. 接受追问，最后说清“不保证什么、怎样验证”。

优先顺序：Q03/Q09/Q11/Q13/Q17/Q21/Q24/Q25/Q29/Q31/Q32。它们与简历和岗位的联系最直接。之后再补语言细节与扩展场景。

以上答案是训练用参考，不是万能模板；真实面试要听清限定条件，不把一句“看场景”当作分析的替代，也不要为了显得严谨把每道题都讲成三分钟免责声明。
