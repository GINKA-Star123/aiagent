# 下一阶段优化路线

> 路线状态更新（V1.2 规划版）：V1.0 稳定化与协议收敛阶段，以及 V1.1 后端优化已完成。此前章节保留为历史背景与既有验收依据；当前后续规划以本文末尾的「V1.2 整体规划」为准。V1.2 暂不包含 Flutter、Qt 或其它前端分支。

本文档用于记录 AIAgent 下一阶段的主要优化方向。当前阶段不以继续堆叠新功能为核心，而以稳定主链路、统一协议、提升可观测性、固化测试和收敛工程边界为主要目标。

建议下一阶段命名为：

```text
V1.0 稳定化与协议收敛阶段
```

## 一、阶段判断

AIAgent 当前已经形成了较完整的 AI VTuber / Live2D 角色陪伴运行时，覆盖：

- FastAPI 后端 API
- Flutter 移动端主客户端
- Qt 桌面调试端
- Persona 人格系统
- LangGraph 对话主流程
- RAG 知识库
- Mem0 / Qdrant 长期记忆
- 视觉理解与角色图库识别
- ASR / TTS / 语音通话
- Live2D payload 与移动端舞台
- 云部署、限流、任务队列、对象存储与 worker

项目目前的主要问题不是缺少能力，而是已有能力之间的边界、协议、初始化方式、异常路径和测试覆盖还不够稳定。下一阶段应优先让现有系统变得更清晰、更可靠、更容易排查，而不是继续增加平行模块。

## 二、阶段总目标

下一阶段的目标可以概括为六句话：

1. 主聊天链路稳定可用。
2. Flutter 与后端协议稳定一致。
3. Runtime 初始化不再被可选重型依赖拖垮。
4. Graph 每个阶段可观测、可降级、可排错。
5. RAG、Memory、Vision、TTS、Live2D 等能力有明确质量基线。
6. 测试、文档、配置和部署形成可重复的交付流程。

## 三、基本开发原则

后续优化应遵守以下原则：

- API route 保持薄封装，不在 route 中堆业务流程。
- Runtime 和 Graph 承担主业务编排。
- 外部模型、数据库、音频、Live2D runtime 适配放在 `integrations/` 或 service 层。
- Persona、RAG、Memory、Vision、Live2D 等领域规则放在 `aiagent/` 对应模块。
- Flutter 是当前 V1.0 主交付端，Qt 是调试端。
- Mock 模式必须能跑通主链路，真实 provider 失败时要能降级。
- 新增或修改 API 字段时，同步更新客户端模型和文档。
- 新增核心行为时，至少补充单元测试、API contract test 或 smoke test。

## 四、P0：主链路稳定与协议收敛

P0 是下一阶段最优先的工作。目标是让后端主接口、移动端协议和运行时初始化稳定下来。

### 4.1 API 响应统一

当前 `/chat` 与 `/chat/multimodal` 已经较接近统一响应，但部分 route 仍在手写 JSON。后续应统一使用 `apps.api.response_utils`。

重点接口：

- `GET /health`
- `GET /ready`
- `GET /runtime/diagnostics`
- `POST /session/open`
- `POST /chat`
- `POST /chat/multimodal`
- `POST /voice/transcribe`
- `POST /voice/realtime/start`
- `POST /voice/realtime/turn`
- `POST /voice/realtime/end`
- `GET /memory/user/{user_id}`
- `DELETE /memory/user/{user_id}`
- `GET /live2d/stats`
- `POST /live2d/preview`

统一成功响应应包含：

```json
{
  "ok": true,
  "request_id": "..."
}
```

统一失败响应应包含：

```json
{
  "ok": false,
  "stage": "...",
  "error": "...",
  "request_id": "..."
}
```

聊天类响应字段应继续保持一致：

- `output_id`
- `reply`
- `base_reply_text`
- `emotion`
- `motion`
- `expression`
- `audio_path`
- `audio_url`
- `audio_segments`
- `audio_segment_urls`
- `audio_segment_texts`
- `live2d_command_path`
- `live2d`
- `metadata`
- `request_id`

验收标准：

- Flutter 端可以用同一套模型解析 `/chat`、`/chat/multimodal`、`/voice/realtime/turn` 的核心回复字段。
- 所有核心 API 错误都能在客户端显示 `stage`、`error`、`request_id`。
- 后端日志可以通过 `request_id` 追踪一次请求。

### 4.2 Runtime 初始化解耦

当前 runtime 装配会集中创建 LLM、RAG、Memory、Vision、ASR、TTS、Live2D 等组件。后续应减少冷启动失败面。

优化方向：

- 将重型依赖改为 lazy init。
- RAG embedding、Vision CLIP、Mem0/Qdrant、ASR 模型不应在普通文本聊天冷启动时全部强制加载。
- 每个能力模块暴露状态：`available`、`degraded`、`disabled`、`error`。
- 主聊天在 RAG、Memory、Vision、TTS、Live2D 不可用时仍可返回文本。
- Runtime 初始化错误按模块记录，不要全部折叠成 `runtime_init`。
- 给 runtime 单例增加并发冷启动保护，避免多请求同时初始化。

验收标准：

- Mock 配置下 API 冷启动可以稳定完成。
- 关闭或缺失 RAG / Vision / Live2D 资源时，文本聊天仍可返回。
- `/runtime/diagnostics` 能说明哪个模块不可用，以及建议动作。

### 4.3 主聊天 smoke 固化

下一阶段应优先建立 mock 模式下的主链路 smoke。

最低覆盖：

- runtime 能构建。
- `/health` 返回成功。
- `/ready` 返回合理状态。
- `/chat` 能返回统一字段。
- `/chat/multimodal` 在 mock vision 下能返回统一字段。
- `/session/open` 能返回 presence opening。
- TTS mock 不阻断聊天。
- Live2D mock / noop 不阻断聊天。

验收标准：

- 本地执行一条命令即可完成主链路 smoke。
- CI 或本地测试失败时能明确指出阶段。

## 五、P1：Graph 可观测性与流程优化

P1 的重点是让主图流程更可控。当前主图是线性流程，结构清晰，但耗时、失败、跳过和降级还需要更细粒度表达。

### 5.1 Graph 阶段耗时

建议为以下阶段记录耗时：

- `prepare_context_ms`
- `vision_graph_ms`
- `memory_retrieve_ms`
- `state_graph_ms`
- `planner_graph_ms`
- `rag_graph_ms`
- `llm_graph_ms`
- `memory_store_ms`
- `response_packet_ms`
- `tts_ms`
- `live2d_ms`

这些字段可进入 `metadata`，也可逐步进入结构化日志。

验收标准：

- 一次 `/chat` 响应能看到主要阶段状态。
- 一次慢请求可以判断慢在 LLM、RAG、Vision、TTS 还是其他阶段。

### 5.2 条件分支与降级

当前主图虽然可以跳过 Vision，但整体仍偏线性。后续应逐步使用更明确的条件分支。

优化方向：

- 文本轮次不进入视觉分析。
- Planner 明确不需要 RAG 时跳过 RAG。
- RAG 检索失败时返回空上下文并记录 `rag_error`。
- Memory 检索失败时返回 `无长期记忆。` 并记录 `memory_error`。
- Memory 写入失败不影响当前回复。
- TTS 失败不影响文字和 Live2D payload。
- Live2D dispatch 失败不影响文字和音频。

验收标准：

- 任一可选模块失败时，主聊天可以降级返回。
- 响应 metadata 中可以看到失败模块和原因。

### 5.3 会话与线程边界

当前短期 LLM 记忆主要按 `user_id` 作为 thread id。后续需要明确以下概念：

- `user_id`：用户身份。
- `session_id`：一次会话。
- `turn_id`：一次输入输出回合。
- `request_id`：一次 HTTP 请求。
- `output_id`：一次输出事件。

优化方向：

- 避免所有上下文都只挂在 `user_id` 上。
- 移动端 session open 与聊天 session 关系应明确。
- 语音通话 call id 与普通聊天上下文关系应明确。

验收标准：

- 同一用户不同 session 的短期上下文策略明确。
- 长期记忆和短期对话不会混用身份字段。

## 六、P1：智能体质量优化

这一部分目标是提升角色回复质量、知识准确性、记忆可靠性和多模态可信度。

### 6.1 Persona 质量

当前默认 persona 是乐正绫，风格配置已经较完整。后续应从 prompt 配置升级为可测试行为。

优化方向：

- 建立 persona 回归测试集。
- 覆盖问候、闲聊、情绪安慰、角色设定、知识问答、多模态图片、拒绝暴露 AI 身份等场景。
- 检查回复是否过长、是否像客服、是否机械复述、是否暴露系统身份。
- Persona 的文本风格、TTS 声音、Live2D 动作应保持一致。
- Mock 回复不应只是简单回显用户输入，可逐步变成角色化 fallback。

验收标准：

- 典型输入下能保持乐正绫口吻。
- 不使用 emoji。
- 不自称 AI。
- 回复不过度长篇说明。

### 6.2 RAG 知识库质量

当前知识库主要围绕 VSinger / 虚拟歌手资料和直播基础知识。下一阶段应建立检索质量基线。

优化方向：

- 为乐正绫、洛天依、言和、VSinger、歌曲、设定、应援词建立问答评测集。
- 给文档增加 metadata：角色、主题、来源、更新时间、可信等级。
- 优化中文别名，例如阿绫、天依、龙牙、墨姐、清弦等。
- 根据文档类型调整 chunk 策略。
- 索引重建默认异步化。
- 文档变化后标记索引过期。
- embedding 维度变化时提供重建提示。

验收标准：

- 常见角色设定问题能召回正确文档。
- RAG 低相关时不会强行注入。
- 回复不会编造知识库没有的内容。

### 6.3 长期记忆质量

长期记忆是陪伴型 Agent 的核心，但必须少而准。

优化方向：

- 明确记忆类型：用户偏好、身份信息、关系进展、长期目标、边界、最近话题。
- 写入前去重。
- 写入前做敏感内容过滤。
- 写入记录保存 category、importance、reason、source、created_at。
- 记忆检索进入 prompt 前做压缩。
- 记忆写入异步化，失败不影响当前回复。
- 用户可以查看、搜索、清空自己的长期记忆。
- 当前返回空的 profile memory 能力要么实现，要么明确标记为未启用。

验收标准：

- 不该记的内容不写入。
- 已记过的偏好不重复写。
- 用户可以清空长期记忆。
- 记忆不可用时聊天仍可继续。

### 6.4 视觉可信度

视觉链路已经覆盖图片保存、角色图库检索、视觉模型分析、上下文注入和 Live2D 建议。下一步要避免误识别和乱推断。

优化方向：

- 严格校验视觉模型输出 schema。
- 区分角色候选和最终确认。
- 角色识别低置信度时使用保守表达。
- 不把所有图片都强行解释成角色图。
- 图片类型分类保持清晰：character、daily、food、travel、screenshot、document、object 等。
- OCR、场景描述、角色识别分开处理。
- 上传图片限制大小、格式和异常文件。
- 视觉结果进入长期记忆前必须经过策略判断。

验收标准：

- 角色图能识别候选。
- 日常图片能自然描述。
- 低置信度不强行确认角色身份。
- 不推断真实人物身份。

## 七、P1：语音与 Live2D 体验优化

语音和 Live2D 是角色陪伴感的关键表达层。

### 7.1 语音链路

优化方向：

- ASR、LLM、TTS 分别记录耗时。
- 语音通话状态明确：连接中、聆听中、识别中、思考中、播放中、错误。
- 支持用户说话时打断当前播放。
- 空转写不触发无意义回复。
- TTS 分段策略稳定，避免空段和过长段。
- 音频 URL 生成规则统一，Flutter 可直接播放。
- 云部署时 realtime call 状态从内存迁移到 Redis 或其他共享存储。

验收标准：

- 语音通话能稳定 start、turn、end。
- TTS 失败不影响文字回复。
- 播放和后端 speaking state 不明显错位。

### 7.2 Live2D 链路

当前后端 Live2D profile 和背景存在，但真实 `model3.json` 资源尚未完整放入。Flutter 端有内置过渡 Live2D WebView 资源。

优化方向：

- 补齐正式 Live2D 模型资源。
- 统一 emotion、expression、motion、background 的映射。
- Live2D payload 增加 schema version。
- 后端只负责 payload 时，移动端负责模型加载和动作执行。
- `/live2d/preview`、`/live2d/stats`、`/live2d/runtime/*` 继续作为调试工具。
- 客户端要能处理未知表情、未知动作和缺失字段。
- Presence 开场、聊天回复、视觉建议使用同一套 Live2D 语义。

验收标准：

- 模型能加载。
- idle、说话、表情切换、动作播放、背景切换都可验证。
- Live2D payload 缺字段不会导致客户端崩溃。

## 八、P1：Flutter 主客户端优化

Flutter 是当前 V1.0 RC 主交付端，应优先保证协议一致、错误友好和状态清晰。

优化方向：

- 拆分过大的 `app/app.dart`。
- API model 与后端字段保持一一对应。
- 网络错误展示 `stage`、`error`、`request_id`。
- 设置页加强 API 地址校验，提醒真机不要使用 `127.0.0.1`。
- 聊天历史保存文本、图片、音频、metadata、memory status。
- Live2D payload 使用统一解析模型。
- 语音通话页明确状态流转。
- Release 构建检查签名配置。
- 增加 Flutter model tests。

验收标准：

- 后端错误不会导致 App 崩溃。
- 用户可以理解当前是网络问题、后端问题还是模型问题。
- Live2D、音频、聊天消息状态保持一致。

## 九、P2：云部署与运维优化

云侧已经具备限流、任务队列、对象存储、GPU client、worker 等基础设施。下一阶段应继续提升可恢复性和可排障性。

优化方向：

- 明确 `/ready` 与 `/cloud/ops/readiness` 的不同用途。
- admin API 必须强认证。
- Redis 不可用时按接口决定 fail-open 或 fail-closed。
- 任务队列记录耗时、重试次数、最后错误、dead-letter 原因。
- worker 处理任务时记录 task_id、worker_id、耗时和结果。
- realtime call 状态不要依赖单进程内存。
- 对象存储统一 local / s3 / cos 命名和行为。
- GPU 熔断状态进入 diagnostics。
- 生产日志支持 request_id 检索。

验收标准：

- 云环境可以通过 readiness 判断是否可接流量。
- 重建任务失败后可查看、重试、进入 dead-letter。
- 管理接口不会暴露敏感配置。

当前测试数量较少，下一阶段应先补主协议和主链路测试，而不是追求覆盖率数字。

### 10.2 API Contract Tests

- `/health`
- `/ready`

- `/voice/realtime/start`
- `/voice/realtime/turn`
- `/voice/realtime/end`

### 10.3 Runtime Smoke Tests

## 十一、配置与文档同步

配置项较多，后续必须防止源码、`.env.example` 和文档不一致。

优化方向：

- `docs/config-reference.md` 与 `config/settings.py` 同步。
- `.env.example` 覆盖源码实际支持的配置项。
- 补充 ASR API provider 配置说明。
- 补充云模式配置组合。
- 补充 mock、本地文本、多模态、本地语音、Live2D 调试、云部署等配置模板。
- 过期文档内容及时清理或标注。
- 新增 API 字段时同步更新 API 协议文档。
- 新增可观测性字段时同步更新观测性文档。

验收标准：

- 新人可以只读 README 和 docs 完成本地 mock 启动。
- 配置项在文档中能找到用途、默认值和影响范围。

## 十二、仓库治理与清理

当前工作区存在一些历史状态和本地资产目录，需要明确治理方式。

优化方向：

- 决定 Flutter 是否继续作为内嵌独立仓库，或正式纳入 monorepo。
- 决定 Qt 调试端是否纳入版本管理。
- 清理 `pyproject.toml` 中不存在的历史包路径。
- 处理 `stage.md` 当前删除状态。
- 清理或修复 `.pytest_cache` 权限问题。
- 明确 `data/` 下哪些是示例资产，哪些是本地私有数据。
- 大模型、缓存、音频生成物、上传文件保持不入仓。
- 建立格式化和 lint 约定。

验收标准：

- `git status` 不再混杂无解释的历史状态。
- 文档能解释哪些目录被忽略但仍是运行资产。
- 开发者不会误把缓存、模型、密钥或用户数据提交。

## 十三、安全与隐私

AIAgent 会处理文本、图片、音频和长期记忆，安全与隐私需要前置。

优化方向：

- 日志不输出 API key、Authorization、完整图片 base64。
- prompt 如需记录，只记录摘要、长度或 hash。
- 上传文件限制大小、类型和路径。
- 用户长期记忆支持查看、删除、清空。
- 敏感个人信息不自动写入长期记忆。
- admin API 强认证。
- 生产环境 CORS 不使用宽松默认值。
- 云配置快照不暴露 secret。
- 视觉不推断真实人物身份。
- 高风险请求同时做系统级拒绝和角色内温和拒绝。

验收标准：

- 日志可排障但不泄露密钥和隐私。
- 用户可以控制自己的长期记忆。
- 管理接口不会被普通客户端调用。

## 十四、建议执行顺序

建议按以下顺序推进：

1. API 响应统一。
2. Runtime 初始化解耦。
3. Mock 主链路 smoke。
4. Graph 阶段耗时与 metadata。
5. Flutter API model 对齐。
6. Live2D 真实资源状态确认。
7. RAG 评测集与检索质量。
8. Memory 策略、去重和删除能力。
9. Vision schema 与低置信度策略。
10. 语音通话状态与打断。
11. 云 readiness、任务队列和 admin 安全。
12. 文档、配置、仓库治理收尾。

## 十五、暂不建议优先做的事项

下一阶段暂不建议优先投入：

- 新增第二套 Web 控制台。
- 新增平行 Live2D dispatcher。
- 新增第二套 RAG 或 Memory 实现。
- 直接上复杂多 Agent 架构。
- 在协议未稳定前做大规模 UI 改版。
- 在测试未固化前继续增加大量 provider。
- 在真实模型资源未交付前深度优化后端 Live2D runtime。

这些事项并非不重要，而是当前投入产出比不如主链路稳定化。

## 十六、阶段完成标准

当以下条件满足时，可以认为本阶段基本完成：

- Mock 模式下后端主链路稳定通过测试。
- Flutter 可以稳定调用 `/session/open`、`/chat`、`/chat/multimodal`、`/voice/realtime/*`。
- 核心 API 响应字段统一，错误响应都带 `stage` 和 `request_id`。
- Runtime 可以在部分外部能力不可用时降级。
- Graph metadata 能显示主要阶段状态和耗时。
- RAG、Memory、Vision 至少各有一组质量回归样例。
- Live2D payload schema 稳定，客户端能容错。
- 配置文档和 `.env.example` 与源码一致。
- 云 readiness、任务队列和 admin 接口有清晰安全边界。
- 项目文档能指导新人完成本地 mock 启动、后端 smoke 和 Flutter 调试。

完成这一阶段后，项目才适合继续进入更高质量的真实模型联调、正式 Live2D 资源接入、移动端正式发布和云端长期运行优化。

## V1.2 整体规划：Agent 质量、安全治理与后端工程化

V1.2 暂不包含 Flutter、Qt、Web 控制台或其它前端分支。范围包括 Python API、Runtime/Graph、RAG/Memory/Vision/Voice 后端能力、数据与模型接入、Cloud/Worker、部署配置、后端测试和文档。Rust 是安全方向的候选实现语言，仅用于威胁建模后确认适合且有明确收益的窄边界组件；不预设重写 FastAPI，也不为了使用 Rust 而额外拆分服务。

建议阶段名称：

V1.2 Agent 质量、安全治理与后端工程化阶段

- 数据质量、数据生命周期、后台维护任务和可恢复性。

### 3. 安全是主线之一，具体目标待风险评估确定

安全是 V1.2 的重要目标，但不是 V1.2 的全部。当前尚未决定要集中解决哪一种安全问题，因此本规划先保留目标选择空间，不预先指定“必须做文件扫描器”“必须重写鉴权”或“必须交付 Rust 服务”。第一阶段结合现有实现、数据流和部署方式，选出一至两个最值得处理的高风险目标，并形成明确的范围、威胁假设和验收方式。

安全目标候选包括：

- 用户身份与资源所有权，重点检查跨用户访问和客户端可控身份字段。
- 图片、音频及通用上传的输入验证、解析资源限制和文件生命周期。
- 用户隐私、长期记忆、日志、诊断和数据删除治理。
- 管理面、Secret、部署凭据及供应链风险。
- Provider、工具或检索内容进入 Agent 后的信任边界和滥用影响。

选择目标时按风险影响、现实暴露面、当前控制缺口、可验证程度、实施成本排序。不要因为 Rust 是预期语言就倒推安全目标。

威胁模型至少覆盖以下资产：

- API 管理凭据、模型 Provider 密钥、数据库凭据和部署 Secret。
- 用户文本、图片、音频、长期记忆、上传文件和生成内容。
- 用户身份、会话、语音 call、任务和对象存储 key 之间的所有权关系。
- Cloud 管理接口、队列、Worker、Redis 键空间和对象存储 Bucket。
- 生产镜像、依赖包、构建产物和发布凭据。

威胁场景至少包括：

- 未授权访问或越权读取、修改、删除其他用户的数据。
- 伪造身份 Header、代理 Header、request_id 或资源 ID 绕过控制。
- 恶意或畸形文件、路径穿越、文件类型混淆、资源耗尽和解析器漏洞。
- Prompt injection、检索内容污染、模型输出不可信导致的工具或数据边界绕过。
- 凭据进入日志、错误响应、配置快照、任务 payload、构建产物或仓库历史。
- Redis、对象存储、LLM、ASR、TTS 或 Worker 故障造成状态损坏、重复执行或跨用户影响。
- 依赖供应链投毒、未固定依赖、构建环境不可信和镜像中残留 Secret。

每项威胁记录：资产、入口、攻击前提、影响、现有控制、剩余风险、验证方法、负责人和处置优先级。优先使用 STRIDE 或同等结构化方法，不要求引入昂贵的新平台。

威胁模型完成后，按高风险且边界稳定的任务选择 Rust 组件；若没有适合 Rust 的窄边界，不强行引入 Rust，改为将威胁模型中的控制落到现有 Python/API/部署层并记录决策依据。

### 4. Rust 在安全方向中的定位

候选方向按优先级评估，不在路线图阶段提前定案：

1. **不可信文件预检组件**：解析文件名、魔数、大小、扩展名与声明 MIME 的一致性，计算 Hash，拒绝路径穿越和畸形输入。Rust 只负责纯解析与校验，不负责业务授权或对象存储写入。
2. **Secret 扫描与发布门禁工具**：扫描待发布配置、日志样例、工件清单和仓库差异中的密钥模式。优先评估成熟扫描器；只有存在 AIAgent 特定规则或集成缺口时才实现 Rust CLI。
3. **高吞吐内容边界过滤器**：只有在基准证明 Python 过滤成为显著瓶颈，且规则可以确定性表达时评估。模型安全策略和语义判断仍不能简单下放为正则过滤。
4. **签名/摘要验证工具**：如果未来需要在 Worker 或离线导入路径验证制品完整性，优先使用成熟标准库和既有格式，不设计自有密码协议。

Rust 组件决策门槛：

- 威胁模型明确指出该组件减少什么风险，失败时影响范围可控。
- 输入/输出 schema、最大输入大小、错误码、超时和版本兼容有书面约定。
- Python 侧已有同一 Contract 的参考实现或清晰的独立测试向量。
- 与 Python 调用边界相比，Rust 带来可度量的安全、性能或隔离收益。
- 维护者能够维护 Cargo 依赖、漏洞响应、跨平台构建和发布产物。
- Rust 组件离线可测，不需要访问用户生产数据或真实 Secret。
- 通过决策记录说明采用 Rust、继续使用 Python 或采用成熟工具的理由。

优先采用进程内窄接口（例如 Python binding）或明确版本化的 CLI/stdio 协议。只有确实需要独立故障域、权限隔离、资源限制或多语言复用时，才评估本地独立进程/服务。不得仅因语言不同就增加网络服务和部署拓扑。

Rust 实现要求：

- 使用稳定版 Rust 和可重复的锁文件构建；提交 `Cargo.lock`（若仓库以可执行安全工具为目标）。
- 输入反序列化后做边界校验，限制字节数、集合大小、嵌套深度和处理时间。
- 默认避免 `unsafe`；确需使用时需逐处记录理由、审查和专门测试。
- 使用成熟加密库，不自创加密算法或签名格式。
- 统一错误码，不把内部路径、Secret 或原始用户内容带入错误消息。
- 对崩溃、超时、非零退出、版本不匹配和空输出定义明确的 fail-open/fail-closed 行为。
- 不把 FFI panic、Rust panic 或 CLI stderr 未过滤地传给 API 响应或普通日志。

### 5. V1.2 多主线工作阶段

V1.2 不是只做安全的连续项目。以下阶段覆盖 Agent 质量、性能与成本、执行状态一致性、安全、Cloud/Worker、数据治理及交付工程。前一阶段建立共同基线；其余方向按依赖关系分批实施，安全与 Agent 质量不互相取代。E1 至 E3 是安全目标候选，不要求全部实施；V1.2-A/V1.2-D 审阅后仅选择风险和收益最明确的有限子集。V1.2-A2 是执行状态与交付门禁的前置批次，其内容不参与优先级取舍。

#### V1.2-A：整体基线与目标审阅

工作项：

- 汇总 V1.1 已有的 API Contract、smoke、RAG 评测、Memory/Vision/Voice 测试和 Cloud 运维测试，标注可复用内容与实际缺口。
- 选取少量代表性 Agent 样例，分别记录检索、记忆、视觉可信度、角色行为和降级表现；区分 Mock 与真实 Provider 结果。
- 记录关键 API/Graph/provider 的延迟、错误率、超时率、并发和可用成本指标；标记样本量和环境，避免用不充分数据得出结论。
- 绘制主要后端数据流和信任边界，整理安全风险候选，但在审阅前不锁定最终安全专项。
- 汇总 Cloud/Worker 的关键故障模式、当前恢复方式和未验证假设。
- 输出 V1.2 目标矩阵：方向、当前基线、拟解决问题、优先级、预计批次、验收证据和非目标。
- 盘点执行状态现状：逐个确认会话、LLM 线程、人格缓存、记忆、限流与指标分别存放在进程内还是共享存储，记录当前 Worker 并发配置与由此产生的可见缺陷。
- 盘点交付基线现状：入口测试命令、是否存在 CI、依赖声明来源与锁定情况、镜像基础版本与本机运行版本是否一致。
- 初步评估 Rust 候选问题，ADR 可以暂定“不引入 Rust”。

验收：

- 各条主线都有可说明的起点、目标和验证方法；用户可审阅后再确认优先级，前端不作为依赖。
- **A 阶段必须产出可执行物，而不只是文档**：至少一个可重复运行的基线脚本（一条命令产出延迟、错误率、质量矩阵的机器可读结果）与对应运行说明；5 份审阅材料允许晚于脚本完成。
- 执行状态现状与交付基线现状各有一页结论，明确列出“当前已经存在的缺陷”和“仅属于优化空间的问题”，二者分开。

#### V1.2-A2：执行状态一致性、CI 门禁与依赖固化

本阶段处理已经存在的功能缺陷与交付地基，属于后续所有批次的前置条件，不随优先级审阅被下调。

工作项：

- 会话状态外置：将 LLM 线程检查点、人格运行时缓存、线程与用户映射从进程内存迁至共享存储（Redis 或等价方案），并规定 TTL、序列化兼容与版本升级方式。
- 跨进程清理语义：使用户长期记忆清空、会话清理、限流与并发计数在全部 Worker 上一致生效，避免只清理当前进程。
- 指标与熔断状态聚合：将进程内指标、GPU 熔断计数与内存兜底的限流状态改为可跨 Worker 读取或聚合，确保面板与熔断判定不再各算一份。
- 多 Worker 一致性验收：以生产默认 Worker 并发配置运行端到端场景，证明同一用户多轮对话的短期记忆连续、清空操作全局生效。
- 迁移与回滚：提供“进程内 → 共享存储”的切换开关与回滚路径，在共享存储不可用时按已声明的失败策略降级，并记录用户可见影响。
- CI 门禁：建立最小可行流水线（静态检查、单元测试、API 契约测试、Mock 冒烟、配置一致性检查、仓库卫生检查），作为后续批次合并的必过条件。
- 分层测试策略：明确哪些检查在每次变更运行、哪些按计划运行，说明重依赖与模型下载不进入常规流水线的理由，避免为追求“全量跑”而放弃门禁。
- 依赖单一真源：确定 Python 依赖的唯一来源并锁定版本，处理与现有 requirements 文件的关系，提供校验命令防止漂移。
- 容器与运行时对齐：生产镜像使用非 root 用户、限制可写目录，并使镜像内解释器版本与本机开发版本一致或明确记录差异。

验收：

- 在生产默认 Worker 并发下，同一会话多轮对话的短期上下文连续率 100%，清空操作在所有 Worker 上生效。
- 共享存储不可用时的降级行为与用户可见错误阶段符合已声明策略，且不会静默分叉会话状态。
- 流水线可重复运行并在失败时给出可定位信息；静态检查、单测、契约、冒烟、配置与卫生检查全部纳入。
- 依赖有唯一来源与锁定文件，并存在防止漂移的校验命令。
- 生产镜像非 root、非开发工具，且解释器版本差异有结论（对齐或书面记录）。

#### V1.2-B：Agent 质量与后端评测闭环

工作项：

- 扩充 RAG 评测问题，覆盖别名、事实型问题、无答案问题、易混淆问题及低相关检索；检查召回、排序和不应注入上下文的情况。
- 在检索级指标之外补答案级指标：回答是否被检索内容支撑、引用是否可追溯到具体片段、应当拒答时是否拒答；检索命中不等同于回答有据，两者分开报告。
- 答案级评测先采用确定性规则（引用是否落在本次注入的上下文中）与小规模人工标注集；引入模型评审时需要单独说明成本、稳定性与不一致样例的处理方式。
- 为 Memory 建立写入、去重、冲突、遗忘/删除、禁用和错误记忆影响回答的回归样例。
- 为 Vision 建立角色图、日常图片、文档/截图、非角色图片和低置信度场景样例，检查结构稳定与保守表达。
- 为 Persona 和主聊天建立小型服务端回归集，覆盖闲聊、知识问答、情绪支持、上下文冲突和能力降级。
- 明确评测运行模式、数据版本、通过阈值和失败样例归档方式；不提交真实用户隐私数据。
- 将 Mock contract/smoke 与真实模型质量评估分开报告。
- 把可在离线环境稳定运行的评测入口接入 V1.2-A2 建立的流水线，使质量退化能在合并前被发现；依赖真实模型或重资源的评测按计划运行，但必须有固定命令与结果归档。

验收：核心后端 Agent 能力各有可重复的评测入口和失败样例；质量回退能定位到检索、策略、上下文、生成或降级环节；至少一项答案级指标与一项检索级指标进入常规门禁。

#### V1.2-C：Runtime/Graph 性能、成本与容量

工作项：

- 用代表性请求测量冷启动、稳态、并发和可选能力关闭时的延迟，报告 P50/P95、样本数及测试环境。
- 根据阶段 metadata 定位 Graph 和 Provider 的主要耗时、重复工作、同步 I/O 阻塞和不必要初始化。
- 记录 LLM、Embedding、Vision、ASR、TTS 的调用次数、Token 或可获得的成本代理指标，估算典型请求和高峰容量。
- 为请求总 deadline、阶段超时、并发上限、输入/输出上限和重试预算设定合理边界。
- 对缓存提出失效、用户隔离、隐私和一致性要求；仅在基准证明有收益后实施缓存。
- 每项性能优化都同时跑正确性和质量回归，避免以局部速度提升换来质量或可靠性退化。

验收：主要瓶颈由数据确认，关键路径有可重复基准；至少完成一项有量化结果的后端优化或形成“不值得优化”的证据。

#### V1.2-D：安全资产盘点与威胁模型

工作项：

- 绘制外部请求到 API、Runtime/Graph、Provider、数据库、对象存储和 Worker 的数据流。
- 列出管理接口、普通用户接口、内部任务入口和部署入口的信任边界。
- 明确每种 ID 的来源和用途：`user_id`、`session_id`、`call_id`、`task_id`、`request_id`、`object_key`。
- 检查授权是否基于服务端认证身份，而不是客户端可控字段。
- 形成风险清单，并将每项分成 P0（可导致跨用户/凭据/生产控制面风险）、P1（显著可靠性或隐私风险）、P2（纵深防御）。
- 产出 Rust 候选组件 ADR，允许结论为“当前不引入 Rust 组件”。
- 本阶段必须收口，不能停留在“候选清单”：明确选定一至两个本版本要处置的安全目标，同时给出一份“本版本不做”的安全事项清单及理由；两者都进入目标矩阵。

验收：

- 高风险数据流有负责人、控制措施和可执行测试；Rust 选型有证据，而不是预设结论。
- 安全目标有明确截止点：选定的目标进入实现批次，未选中的以风险登记形式保留，不自动扩展为本版本范围；允许结论为“本版本不做安全专项，仅保留风险登记与既有控制”。

#### V1.2-E1：身份、授权与资源所有权（候选安全目标）

只有当 V1.2-D 威胁评估将该领域列入优先范围时，才按本节开展实现；未选中的内容保留为风险记录，不自动扩展为本版本必做范围。

工作项：

- 盘点所有基于 `user_id`、`username`、Header、call id、记忆 ID、上传 ID 的资源访问。
- 让业务授权从可信认证主体派生，不把请求体中的 `user_id` 直接等同于已认证用户。
- 为 Memory 查看、编辑、置顶、合并、删除和禁用功能增加跨用户隔离测试。
- 为 Vision 文件、对象存储 key、Realtime call 和任务状态增加 owner 绑定或明确的内部服务权限。
- 管理接口统一认证依赖，并覆盖缺失、错误、弱配置和权限不足场景。
- 明确开发 Mock 身份与生产身份的隔离，禁止生产静默回退到固定 guest 身份作为授权依据。

验收：所有用户资源接口都有“本人可访问、其他用户不可访问”的正反向 Contract 测试；管理面和用户面权限无隐式混用。

#### V1.2-E2：上传与数据解析安全（候选安全目标）

工作项：

- 统一图片、音频和通用对象上传限制：请求体大小、文件大小、允许类型、扩展名、魔数和解析失败语义。
- 避免只信任客户端 `Content-Type` 或扩展名；对不同业务定义允许格式列表。
- 文件名只用于显示和诊断，实际存储 key 使用服务端生成值；对象路径不能来自未验证的用户路径。
- 明确归档文件、文档、图像和音频解析器的超时、内存上限、页数/帧数上限及异常处理。
- 为恶意 MIME、双扩展名、空文件、截断文件、超大尺寸、Unicode 混淆、路径穿越和解析器异常建立测试样本。
- 上传文件和派生缓存制定 TTL 与清理策略；明确敏感文件的日志禁止项。

Rust 若承担文件预检，仅处理有界输入并返回规范化元数据；实际文件落盘、用户授权、对象存储写入仍由受控服务流程完成。需要评估 Rust 与 Python 图像/音频解析库的攻击面，不因 Rust 语言本身就默认安全。

验收：所有上传入口都有一致的限制、拒绝阶段和清理行为；恶意样例不会导致路径越界、无界内存/CPU 占用或跨用户文件访问。

#### V1.2-E3：密钥、日志、隐私与留存（候选安全目标）

工作项：

- 盘点 Secret 来源、注入方式、访问主体、轮换方式和过期方式。
- 确认配置快照仅暴露“是否配置/风险状态”，不暴露 Secret、可逆片段或完整连接串。
- 对日志、异常、任务 payload、死信记录和诊断输出做敏感数据回归扫描。
- 定义 Prompt、用户文本、ASR 文本、图片/音频引用和模型响应的日志策略；默认只记录长度、Hash、阶段、状态和耗时。
- 为记忆、上传文件、Realtime 状态、任务记录和日志分别设定数据保留期及删除责任。
- 设计 Secret 轮换和撤销 runbook；泄漏响应包括定位、撤销、轮换和历史风险判断。
- 对 CORS、可信代理、TLS 终止位置和管理认证做部署检查。

验收：使用合成 canary Secret 扫描 API 响应、日志、任务记录、配置快照和测试产物，结果中不出现原值。

#### V1.2-E4：Rust 安全组件原型与集成（条件项）

只有威胁模型确认存在适合 Rust 的高价值窄边界问题，且 ADR 获得审阅后才实施。若选择文件预检候选，原型范围建议为：

- crate/library 接受有字节上限的输入描述，不接受任意本机路径。
- 返回 `schema_version`、`accepted`、规范 MIME、文件类型、字节数、SHA-256 和稳定错误码。
- 对“声明类型、扩展名、魔数不一致”返回可解释拒绝原因。
- Rust 单测覆盖有效样本、畸形样本、边界大小和超时/资源限制。
- Python Contract 测试验证字段、错误映射、版本兼容和降级行为。
- 对同一批固定样本比较基准实现，保存可重复 benchmark 命令和结果。
- 安全组件失败时按业务风险决定 fail-closed（文件接收/解析）或有限 fail-open（不影响纯文本聊天），不得静默绕过上传安全检查。

第一轮原型不处理真实图片内容语义、不识别人物身份、不调用模型、不接触云凭据，也不提供远程网络 API。

验收：Rust 组件可独立构建和测试，接口有版本化契约，Python 集成失败不会使服务进程崩溃或泄露内部信息；组件确有风险或性能收益，否则记录不采用结论。

#### V1.2-F：Cloud / Worker 故障隔离与数据生命周期

工作项：

- 对 Redis、对象存储、LLM、ASR、TTS 和队列明确逐项 fail-open/fail-closed 策略及用户可见错误阶段。
- 为 Worker 增加任务幂等键、重复投递行为、超时、取消、stale recovery 和死信重放边界。
- 验证 Redis 故障时 realtime 状态不会在多实例中静默分叉；生产配置采用 fail-closed 或明确停用多实例能力。
- 为任务和 call 状态规定 TTL、最大 payload、敏感字段过滤和 PII 保留要求。
- 为用户记忆、上传对象、派生缓存、任务历史和运行日志定义保留期、删除触发点、删除失败处理和审计证据。
- 检查数据备份、恢复副本和测试环境副本是否遵守相同的数据访问与保留要求。
- 对 Provider 重试设置总 deadline、最大 attempts、退避和可重试错误分类，防止级联重试。
- 增加依赖注入故障测试：Redis 断连、超时、对象存储 5xx、Provider 超时、Worker 中止和重复任务。
- 为 readiness 与 liveness 分离依赖检查，确保不因可选能力短暂异常造成不必要的容器重启。

验收：故障注入能证明系统在单个可选依赖失败时隔离影响；重试有上限且不会造成重复副作用；生产 readiness 能准确阻止不可安全接流量的配置。

#### V1.2-G：供应链、构建与发布门禁

工作项：

- 固定 Python 依赖与 Rust crate 版本；对生产依赖执行漏洞审查和升级记录。（Python 依赖的唯一真源、锁定与漂移校验已在 V1.2-A2 完成，本阶段负责依赖漏洞审查与升级记录，不重复建设。）
- 增加 Python dependency audit、Rust `cargo audit`（团队确认工具可用后）和 Secret scan。
- 为 Rust/ Python 测试及生产镜像构建提供离线或可重复的 CI 命令。
- 生产镜像使用非 root 用户，限制写目录，避免把开发工具、模型缓存、测试数据和 Secret 打入镜像。
- 定义镜像标签、SBOM 生成与保存、构建来源和回滚版本。
- 部署前校验 CORS、可信代理、管理 Token、Redis、对象存储和 Mock Provider 等关键组合。
- 为安全门禁定义例外流程：责任人、理由、到期日和补救事项，禁止永久静默忽略。

验收：发布产物可追溯到锁文件和构建版本；Secret scan 和高危依赖门禁结果可审计；发布失败能安全回滚。

#### V1.2-H：多主线集成与版本收尾

工作项：

- 汇总 Agent 质量、性能/成本、安全、Cloud/Worker 和数据治理各主线的验收证据。
- 对已选定的高风险项逐一提供自动验证，或记录有负责人、期限和缓解措施的例外。
- 运行后端 API Contract、Mock smoke、Agent 评测、故障注入、配置预检和供应链门禁。
- 更新 API、评测、安全、配置、数据生命周期、事件响应和部署文档。
- 记录 Rust 组件采用、暂缓或不采用的决策及后续维护责任。
- 形成已知风险和 V1.3 输入；不得用总体通过率掩盖未完成的高风险事项。

### 6. 建议批次顺序与有限交付边界

建议拆成 7 个有明确边界的批次。安全只占其中一条主线，批次顺序依据共同基线和技术依赖安排：

1. **V1.2 目标与基线（V1.2-A）**：汇总 V1.1 后端成果，建立 Agent 质量、性能/成本、执行状态、可靠性、安全和数据治理现状矩阵；产出可重复运行的基线脚本；审阅后确认本版本有限目标。
2. **执行状态一致性、CI 门禁与依赖固化（V1.2-A2）**：修复多 Worker 下会话与线程状态分叉这一已存在的缺陷，建立合并必过的流水线，确定依赖唯一真源并锁定，完成镜像非 root 与版本对齐。本批是后续批次的前置条件。
3. **Agent 质量闭环（V1.2-B）**：完善 RAG、Memory、Vision、Persona/主聊天中最有价值的后端评测与失败回归，补齐答案级指标，并把可离线运行的评测入口接入第 2 批的门禁，不改前端。
4. **性能、成本与容量（V1.2-C）**：测量关键 Graph/Provider 路径，优化经数据确认的热点，设定 deadline、并发和成本观测边界。
5. **选定的安全目标（V1.2-D 与选定的 E 子项）**：根据风险评估选择一至两个安全主题，例如授权隔离、上传解析或数据/Secret 保护；实现对应控制和负向测试，不要求把所有候选安全子项全部做完。
6. **Rust 决策与 Cloud/数据可靠性（V1.2-E4 条件项与 V1.2-F）**：基于 ADR 决定是否做 Rust 窄原型；同时覆盖优先级最高的 Redis/队列/Worker/Provider 故障恢复与数据留存删除。若 Rust 不合适，交付明确的不采用结论，不为了语言目标制造额外服务。
7. **工程交付与 V1.2 收尾（V1.2-G 与 V1.2-H）**：依赖/Secret/镜像门禁的漏洞审查与升级记录、完整后端回归、配置与文档同步、发布清单、已知风险和 V1.3 建议。

每批只设一个主要可验收结果，可在同一主线内配套代码、配置、测试、验证指令和文档。批次 1 审阅后允许调整批次 3 至 6 的优先级，但不扩大前端范围，也不把所有方向塞进单个大版本冲刺。

**唯一不随优先级审阅下调的是批次 2**：多 Worker 下会话状态分叉是当前部署形态下已经存在的功能缺陷（生产默认并发大于 1，而 LLM 线程检查点与人格缓存仍在进程内存中），不是优化空间。若因资源原因必须压缩批次数量，可将批次 2 与批次 6 合并，但其内容不得被删除或后移至收尾批次。

### 7. V1.2 验收标准

V1.2 是多主线版本，完成标准按以下共同门槛审阅：

- **范围受控**：批次 1 形成并经审阅的 V1.2 目标矩阵；安全专项目标从威胁评估中选定，而非默认包揽所有安全候选。
- **Agent 质量**：主要后端能力有可复现评测、版本化样例和质量回归结果；Mock 与真实模型结论分开。
- **性能与成本**：关键路径有可信基准、容量假设和超时/并发/调用预算；优化有前后对照，或有不优化的证据。
- **安全治理**：选定的高优先级威胁得到自动验证、处置或有责任人和期限的风险接受；Secret、身份边界和数据处理有审阅证据。
- **Rust 决策**：若采用，组件的安全问题、窄边界、Contract、构建、测试、故障行为和维护责任明确；若不采用，ADR 说明理由即可，不以 Rust 代码量作为完成条件。
- **Cloud 与数据可靠性**：选定关键依赖有故障及恢复测试；任务、Realtime 和数据留存/删除有明确的副作用、TTL 与恢复规则。
- **执行状态一致性**：在生产默认 Worker 并发下，会话、LLM 线程、人格缓存与记忆状态跨 Worker 一致；跨进程清理生效；共享存储不可用时的降级行为符合已声明策略，不静默分叉。
- **交付治理**：后端 smoke、Contract、选定评测和部署前配置/依赖检查可以重复执行，已知风险及例外可追踪；存在最小可行流水线且是合并必过条件；依赖有唯一真源与锁定文件；生产镜像非 root。
- **范围排除**：Flutter、Qt、Web UI 及其它前端功能不属于 V1.2 验收内容。

### 8. V1.2 暂缓事项

- 不把 V1.2 简化成纯安全项目；也不因安全方向重要而无限扩展为全面安全认证工程。
- 不在风险和数据基线审阅前锁定唯一安全目标，或预设一定要开发某种 Rust 工具。
- 不将 API/RAG/Memory/Realtime 整体重写成 Rust。
- 不自行发明加密算法、认证协议、密码存储格式或 JWT 机制。
- 不把 LLM 输出当作授权决策，也不通过简单正则声称彻底解决 Prompt Injection。
- 不因 Rust 理论性能优势跳过基准、依赖维护评估、跨平台构建和故障语义设计。
- 不同时启动多个新的 Agent 架构、Provider 平台或独立安全服务；一次只推进经审阅的有限主题。
- 不将 Flutter、Qt、Web 控制台、视觉改版、语音 UI 和 Live2D 舞台改造并入本版本。
- 不在执行状态统一之前扩大 Worker 并发、开启多副本水平扩展，或把多实例一致性依赖交给"以后再修"。

### 9. V1.2 启动时的首批审阅材料

进入后续实现批次前，建议先审阅以下材料。安全材料是整体规划的一部分，不代表 V1.2 只围绕安全：

1. `docs/v1.2-scope-and-baseline.md`：V1.1 后端现状、六类主线基线（Agent 质量、安全治理、性能与成本、Cloud 可靠性、会话与状态一致性、数据与工程治理）、优先级、批次、成功指标和明确非目标。
