# V1.2 执行状态一致性与交付门禁

> 本文件是**运行手册**（面向部署与排障），不是设计提案。
> 内容与提交 `ec91ecf`（V1.2 第二批次：多 Worker 执行状态一致性）的实际代码逐项核对；
> 代码一旦变更，请同步更新本文件，并在提交信息中说明改了哪一节。

适用范围：所有会启动**一个以上后端进程**的部署（`uvicorn --workers N`、多容器、多机），
以及需要"同一用户在同一会话里跨 Worker 连续对话"的场景。单进程本地开发可跳过第 4 节之后的内容。

## 1. 组件与数据流

| 组件 | 文件 | 职责 |
| --- | --- | --- |
| 状态模型与异常 | `aiagent/state/shared_state.py` | 常量、`SessionRecord` / `ThreadOwnerRecord`、四类异常（各自带 `stage`） |
| 共享存储实现 | `aiagent/state/redis_state_store.py` | 线程归属索引、会话锁、fence 写入、活跃 persona、清理 |
| 错误重抛守卫 | `aiagent/state/shared_state_guard.py` | `raise_if_shared_state_error()`：防止一致性错误被"阶段降级"吞掉 |
| HTTP 错误契约 | `apps/api/shared_state_errors.py` | 异常 → 409 / 503 / 403（含 `retryable`） |
| 组装 | `apps/core/bootstrap.py` | `build_shared_state_store()` / `build_llm_checkpointer()`，注入 Runner、PersonaManager、EventDispatcher |

一次 `POST /chat` 的关键路径：

~~~text
route(chat.py) → runtime.handle_chat_full(session_id) → EventDispatcher.handle_input
   ├─ resolve_session_id(event) → event.session_id
   ├─ [共享模式] with store.session_lock(session_id, lease_seconds=60)   # 单写者租约
   │     └─ 锁内：MainRunner 各阶段 → LLMRunner.run
   │           ├─ store.register_thread(thread_owner)                    # 线程归属登记
   │           ├─ checkpointer.get_state(thread_id)                      # 短期上下文（RedisSaver）
   │           └─ checkpointer.put(...)                                  # 写回检查点
   └─ 返回 OutputEvent（异常按第 6 节映射为 409/503/403）
~~~

要点：**短期上下文的事实来源是 checkpointer**（共享模式下为 `RedisSaver`）；
进程内的 `conversation_state` 在共享模式下不再参与历史拼装（`aiagent/brain/agent_core.py:52-66`）。

## 2. 标识关系

| 标识 | 来源 | 本批次中的作用 |
| --- | --- | --- |
| `user_id` | 请求体 / 客户端 | 线程归属登记的 owner；共享模式下**必须非空**，否则抛 `SharedStateOwnershipError` |
| `session_id` | `SessionManager.resolve_session_id(event)` | **分布式锁的粒度**：同一会话同一时刻只允许一个 Worker 处理 |
| `thread_id` | 检查点线程键 | 短期上下文与检查点的键，`recent_dialogue_lines(thread_id)` 的历史来源 |
| `turn_id` | `SessionManager.resolve_turn_id` | 轮次标识，用于日志串联 |
| `call_id` | 实时语音链路 | 通话状态（由 `voice_call_store` 管理，与本批次无关） |
| `request_id` | HTTP 中间件 | 与 `metadata` 一起回传，便于把 409/503 关联到具体请求 |

**当前实现约定**：在 LLM 图这一层，`thread_id` 与 `session_id` 取同一个值——
`LLMRunner.run` 登记归属时写的是 `ThreadOwnerRecord(thread_id=…, session_id=thread_id)`
（`aiagent/graphs/llm_graph.py:200-206`），即"一个会话 = 一个线程"。
若将来需要"一个会话多个线程"，必须先扩展这一层的键设计，不能只改调用方参数。

## 3. 共享状态契约（key / 版本 / TTL / 容量 / 序列化）

### 3.1 Key 约定

~~~text
{REDIS_PREFIX}:v12:session:{session_id}           会话记录（SessionRecord）
{REDIS_PREFIX}:v12:session-lock:{session_id}      会话分布式锁
{REDIS_PREFIX}:v12:session-fence:{session_id}     会话 fence 计数器（单调递增）
{REDIS_PREFIX}:v12:thread-owner:{thread_id}       线程归属（ThreadOwnerRecord）
{REDIS_PREFIX}:v12:user-threads:{user_id}         该用户的线程集合（SET）
{REDIS_PREFIX}:v12:persona-active:{scope}         活跃 persona（当前只用 global）
{REDIS_PREFIX}:checkpoint…                        RedisSaver 的检查点与写入键
~~~

- `v12` 是**本批次的命名空间代际**，由 `aiagent/state/redis_state_store.py:87` 的 `_key()` 统一生成。
- 默认 `REDIS_PREFIX=aiagent:v1`，最终形如 `aiagent:v1:v12:thread-owner:chat:u1:abc`。
- 检查点键前缀在 `build_llm_checkpointer()` 中拼为 `{REDIS_PREFIX}:checkpoint` 与 `{REDIS_PREFIX}:checkpoint-write`。

### 3.2 版本与升级

| 项 | 现状 |
| --- | --- |
| schema 版本常量 | `SHARED_STATE_SCHEMA_VERSION = "1.0"`（`shared_state.py:8`） |
| 落盘形式 | 每条记录 `to_dict()` 都带 `schema_version` 字段，便于审计与迁移脚本识别 |
| 读端兼容 | **当前读端不按版本分支**，只校验"必须是 JSON 对象"（`_decode()`，`redis_state_store.py:105-112`） |
| 兼容升级 | 字段只增不改语义时保持 `v12` 与 `1.0` 不变，新旧进程可并存 |
| 破坏性变更 | 必须同时改 ①`_key()` 的代际段（`v12` → 下一代际）②`build_llm_checkpointer()` 的 `checkpoint_prefix`；然后新旧双跑、按会话灰度、靠 TTL 淘汰旧键 |
| 禁止 | 不要"原地改同一批键的语义"；不要在未双跑时直接切代际（会让同一会话在两个代际各写一份） |

### 3.3 TTL、容量与序列化

| 项 | 值 | 位置 |
| --- | --- | --- |
| 会话 TTL | `EXECUTION_STATE_SESSION_TTL_SECONDS`，默认 `86400`（≥300） | `cloud/config.py:89-93` |
| 线程归属 / 用户线程集合 TTL | `EXECUTION_STATE_THREAD_TTL_SECONDS`，默认 `1800`（≥300） | `cloud/config.py:94-98` |
| 活跃 persona TTL | 复用会话 TTL | `redis_state_store.py:295-310` |
| 单用户线程上限 | **100**（`DEFAULT_MAX_THREADS_PER_USER`，当前硬编码，不可配） | `shared_state.py:11` |
| 序列化 | JSON，`ensure_ascii=False` + 紧凑分隔符；值必须是对象 | `redis_state_store.py:101-112` |

超限行为：`register_thread` 写入后检查 SET 基数，超限抛
`SharedStateConflictError("maximum threads per user exceeded")` → 客户端收到 **409**。

## 4. 一致性机制

### 4.1 会话锁（单写者租约）

~~~python
with self.shared_state_store.session_lock(session_id=session_id, lease_seconds=60):
    return self._handle_input_unlocked(event)
~~~
（`aiagent/orchestrator/dispatcher.py:108-122`）

- 获取：`SET key token NX EX lease`；失败即抛 `SharedStateConflictError`（→409），**不阻塞等待、不可重入**。
- 释放：Lua 脚本比对 token 后删除，保证不会误删他人锁。
- 异常语义：锁内业务异常原样上抛（`yield` 位于异常处理范围之外），业务错误不会被包装成"锁失败"。

### 4.2 fence（写序保护）

- `session_lock` 每次成功获取都会 `INCR` `session-fence:{session_id}`，把该值作为 fence 交给调用方。
- `write_session(record, fence)` 用 Lua 校验"当前记录的 fence == 我的 fence"才写入：
  fence 落后返回 0 → `SharedStateConflictError("stale session fence")`；记录已删返回 -1 → `("session was deleted during write")`。
- **现状**：`ensure_session` 与 `write_session` 已实现但**尚未接入请求链路**（全仓只有定义，无调用方）；
  当前主链路依赖"会话锁 + 归属校验 + checkpointer 写入"。见第 11 节。

### 4.3 归属校验

| 操作 | 校验 |
| --- | --- |
| `register_thread` | 已有 owner 且 user_id / session_id 不同 → `SharedStateOwnershipError`（403） |
| `get_thread_owner` | 供 `clear_thread` 在未传 user_id 时反查归属 |
| `delete_thread_registration` | owner 与传入 user_id 不符 → `SharedStateOwnershipError`（403） |
| `LLMRunner.run`（共享模式） | `user_id` 为空 → `SharedStateOwnershipError` |

**前提假设**：同一线程的写入由会话锁串行化；本批次不解决"绕过 Dispatcher 直接调用 Runner"的并发写。

## 5. 跨进程清理语义

| 入口 | 行为 | 生效范围 |
| --- | --- | --- |
| `LLMRunner.clear_thread(thread_id, user_id="")` | 解析 user（入参 → 本地归属 → 共享 owner）→ **先 `checkpointer.delete_thread`，再删 owner 索引** → 清本地缓存 | 所有 Worker |
| `LLMRunner.clear_user_threads(user_id)` | 共享模式下用 `list_user_threads` **跨进程枚举**该用户全部线程，逐个 `clear_thread` | 所有 Worker |
| `LLMRunner.clear_all_threads()` | 本地缓存 ∪ `list_all_threads()`（SCAN `thread-owner:*`），逐个清理 | 所有 Worker |
| `DELETE /memory/user/{user_id}` | 删长期记忆 → `clear_user_threads` → `conversation_state.clear()`（本进程短期视图） | 长期记忆 + 全部 Worker |
| `POST /control/reset-context` | `clear_all_threads()` + `conversation_state.clear()` | 所有 Worker |

**顺序设计（不要改）**：`clear_thread` 先删检查点、后删 owner 索引。
如果索引先删而检查点删除失败，残留检查点将**无法再被定位**（索引是唯一枚举入口）；
反过来先删检查点，即使索引删除失败也能靠 owner 索引重试。

其它约定：

- `clear_thread` 要求 checkpointer 提供可调用的 `delete_thread`，否则抛 `RuntimeError`（不再退回"写空检查点"的老做法）。
- `RedisStateStore.delete_user_threads(user_id)` 目前只被集成测试使用，可作为后续"按用户清理"接口复用。
- 清理**不删 persona-active**：切换人格属于全局状态，不随用户清理回滚。

## 6. 失败与降级矩阵

### 6.1 启动期（`build_shared_state_store` / `build_llm_checkpointer`）

| 配置 | 行为 |
| --- | --- |
| `EXECUTION_STATE_MODE=local` | 不建共享存储；checkpointer 用 `InMemorySaver`。**仅适用于单进程** |
| `MODE=redis` + `REDIS_URL` 空 + `FAIL_CLOSED=true` | 抛 `RuntimeError("redis execution state is required but REDIS_URL is empty")` → Runtime 构建失败 → `/chat` 返回 503 |
| `MODE=redis` + `REDIS_URL` 空 + `FAIL_CLOSED=false` | `build_shared_state_store()` 返回 `None`：**静默降级为进程内**（可用性优先，但多 Worker 会各自持有上下文） |
| `MODE=redis` + Redis 连不上 | `RedisStateStore` 构造时 `ping` 失败 → `SharedStateUnavailableError` → 503 |
| `MODE=redis` + `RedisSaver` 初始化失败 | `SharedStateUnavailableError`，注释明确"拒绝回退到 InMemorySaver"；此分支**不看 `FAIL_CLOSED`**（checkpointer 永远 fail-closed） |
| 未安装 `langgraph-checkpoint-redis` | `RuntimeError("RedisSaver is not installed…")` → 启动即失败（快速失败，不留半可用状态） |

### 6.2 请求期（HTTP 契约）

| 异常 | `stage` | HTTP | `retryable` | 典型触发 |
| --- | --- | --- | --- | --- |
| `SharedStateConflictError` | `shared_state_conflict` | **409** | true | 会话正被其它 Worker 处理；stale fence；单用户线程数超限 |
| `SharedStateUnavailableError` | `shared_state_unavailable` | **503** | true | Redis 连接/ping 失败；RedisSaver 初始化失败 |
| `SharedStateOwnershipError` | `shared_state_ownership` | **403** | false | 线程/会话归属不符；共享模式下 `user_id` 为空 |
| 其它异常 | 各阶段自己的 stage | 原有行为 | — | 不受本批次影响 |

**一致性错误不会被降级吞掉**：主图各阶段的 `except` 分支先调用
`raise_if_shared_state_error(exc)`（`aiagent/graphs/main_graph.py` 的 350 / 404 / 445 / 481 / 521 / 571 行等），
把一致性错误重新抛出，而不是记成"该阶段失败但继续跑"。**新增阶段时务必照做**。

路由侧映射点：`chat.py`（2 处）、`control.py`（3 处）、`multimodal_chat.py`（2 处）、`voice_realtime.py`（2 处）。

| 变量 | 代码默认 | 模板值 | 约束 | 生效位置 |
| --- | --- | --- | --- | --- |

| `EXECUTION_STATE_LOCK_TTL_SECONDS` | `60` | `60` | ≥10 | ⚠️ **当前未生效**：Dispatcher 硬编码 `lease_seconds=60`（`dispatcher.py:120`） |

② 把 `EXECUTION_STATE_MODE` 设为 `local`。

## 8. 部署、迁移与回滚

### 8.1 前置条件

~~~powershell
# 检查点后端
uv pip install --python .venv\Scripts\python.exe langgraph-checkpoint-redis
.venv\Scripts\python.exe -c "import langgraph.checkpoint.redis; print('ok')"

# Redis 可达
.venv\Scripts\python.exe -c "from redis import Redis; print(Redis.from_url('redis://127.0.0.1:6379/0').ping())"
~~~

### 8.2 从 local 切到 redis

1. 确认所有实例连到**同一个** Redis 库（`REDIS_URL` 指向同一个 DB）。
2. 分批重启：先切一个实例，观察 `/chat` 是否出现 409/503。
3. 全部切完后，**存量会话的短期上下文不会自动迁移**：切换前各 Worker 内存里的历史不再被读取，
   切换后第一轮以 Redis 为空开始。建议在低峰或维护窗口执行。
4. 校验：同一 `session_id` 交替打到两个实例，第二轮应能看到第一轮历史（见第 9 节冒烟脚本）。

### 8.3 回滚

| 场景 | 操作 | 注意 |
| --- | --- | --- |
| Redis 短时抖动 | 保持 `MODE=redis`，让请求返回 503（可重试） | 不要改 `FAIL_CLOSED=false`：那会静默退化为进程内，多 Worker 立刻分叉 |
| 需要彻底退回单进程 | 实例数降到 1，再设 `MODE=local` 重启 | 多实例 + local = 上下文分裂，属禁止配置 |
| 检查点后端异常 | 修复 Redis/依赖后重启 | `RedisSaver` 失败是 fail-closed，改 local 等于放弃一致性 |

Redis 数据本身无需回滚：键按 TTL 自然过期（会话 1 天、线程 30 分钟）；
`flushdb` 只允许出现在测试或明确的重置流程中（集成测试里有，生产禁止）。

### 9.2 手工多 Worker 冒烟

~~~powershell
Start-Process .venv\Scripts\python.exe -ArgumentList '-m','uvicorn','apps.api.http_server:app','--port','8000'
Start-Process .venv\Scripts\python.exe -ArgumentList '-m','uvicorn','apps.api.http_server:app','--port','8001'

# 第一轮：实例 A 记住信息
Invoke-RestMethod -Method Post http://127.0.0.1:8000/chat -ContentType 'application/json' -Body '{"user_id":"u1","username":"U","text":"我叫阿岚","session_id":"s-demo"}'
# 第二轮：实例 B 应能引用上一轮
Invoke-RestMethod -Method Post http://127.0.0.1:8001/chat -ContentType 'application/json' -Body '{"user_id":"u1","username":"U","text":"我叫什么","session_id":"s-demo"}'
# 清理后两个实例都不应再看到旧上下文
Invoke-RestMethod -Method Delete http://127.0.0.1:8000/memory/user/u1
~~~

通过标准：① 第二轮能引用第一轮内容（同会话上下文连续率 100%）；
② 任一实例清理后，另一实例下一轮不再包含旧内容；③ 并发打同一 `session_id` 应出现 409 而不是双写。
