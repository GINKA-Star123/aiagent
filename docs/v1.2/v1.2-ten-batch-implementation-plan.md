# V1.2 十批次实施目标

## 一、文档定位

本文根据 `docs/next-stage-optimization-roadmap.md` 中的 V1.2 规划，将后端优化工作收敛为十个可独立验收的批次。

V1.2 的定位是：

```text
Agent 质量、安全治理与后端工程化阶段
```

安全是 V1.2 的重要方向之一，但不是全部。V1.2 同时覆盖 Agent 质量、Runtime/Graph 性能与成本、多 Worker 执行状态一致性、Cloud/Worker 可靠性、数据生命周期和工程交付。

本版本明确不包含：

- Flutter、Qt、Web 控制台或其它前端分支。
- 前端 API model、页面、交互、Live2D 舞台或语音 UI 改造。
- 将整个 Python API、RAG、Memory、Voice 或 Runtime 重写为 Rust。
- 在威胁模型完成前预设必须开发某一种 Rust 安全工具。
- 新增复杂多 Agent 架构、第二套 RAG/Memory 或没有质量基线的新 Provider。

## 二、十批次总览

| 批次 | 主题 | 对应路线 | 核心结果 |
| --- | --- | --- | --- |
| 第 1 批 | V1.2 基线与目标矩阵 | V1.2-A | 用可执行基线确定版本范围和优先级 |
| 第 2 批 | 多 Worker 执行状态一致性 | V1.2-A2 | 会话、线程、人格缓存与清理语义跨进程一致 |
| 第 3 批 | CI、依赖与容器地基 | V1.2-A2 | 建立后续所有批次必须通过的交付门禁 |
| 第 4 批 | Agent 质量评测闭环 | V1.2-B | RAG、Memory、Vision、Persona 有可重复质量基线 |
| 第 5 批 | Runtime/Graph 性能与成本 | V1.2-C | 用数据确认瓶颈并完成至少一项量化优化 |
| 第 6 批 | 威胁模型与安全目标选择 | V1.2-D | 从安全候选中选定一至两个有限目标 |
| 第 7 批 | 选定安全目标落地 | V1.2-E1/E2/E3 | 完成选定安全控制及负向 Contract 测试 |
| 第 8 批 | Rust 安全组件决策与条件原型 | V1.2-E4 | 交付 Rust 原型，或交付明确的不采用 ADR |
| 第 9 批 | Cloud/Worker 故障恢复与数据生命周期 | V1.2-F | 验证幂等、重试、故障隔离、保留与删除行为 |
| 第 10 批 | 供应链门禁与 V1.2 收尾 | V1.2-G/H | 汇总证据，完成发布检查和已知风险登记 |

## 三、共同执行规则

十个批次统一遵守以下规则：

1. 每批只有一个主要可验收结果，不在同一批次混入无关重构。
2. 每批至少包含实现或配置、自动化测试、验证指令、文档影响和回滚说明。
3. 新增 API 行为必须同步 Contract 测试；新增配置必须同步 `.env.example`、云模板和配置文档。
4. Mock smoke 用于证明工程链路可运行，不作为真实模型质量证明。
5. 真实 Provider 评测与离线/Mock 测试分开运行、分开报告。
6. 所有测试数据必须是合成数据、公开数据或经过脱敏的数据，不提交真实用户隐私。
7. 所有性能结论必须记录环境、样本量、请求类型和统计口径。
8. 安全目标由风险评估选择，不以 Rust 代码量作为版本完成条件。
9. 多 Worker 状态分叉属于已存在的功能缺陷，第 2 批不得被取消或推迟到收尾阶段。
10. 前端工作在十批次中始终不进入范围。

## 第 1 批：V1.2 基线与目标矩阵

### 目标

建立 V1.2 的统一起点，用实际代码、测试和可执行数据确认哪些能力已经完成、哪些是功能缺陷、哪些只是进一步优化空间，并据此冻结十批次范围。

### 主要工作

- 盘点 V1.1 已有的 API Contract、Mock smoke、RAG 评测、Memory/Vision/Voice 测试和 Cloud 运维测试。
- 建立 Agent 质量、性能与成本、执行状态、Cloud 可靠性、安全、数据与工程治理六类现状矩阵。
- 选取少量代表性文本聊天、RAG、Memory、Vision、Voice 请求，记录当前状态、错误和阶段 metadata。
- 盘点所有进程内状态与共享状态，包括 session、LLM thread/checkpointer、persona runtime、Memory、Realtime call、限流、熔断和 metrics。
- 记录生产默认 Worker 数、Python 版本、容器版本、依赖来源和当前测试入口。
- 创建一条可重复运行的基线命令，输出机器可读结果，例如 JSON 报告。
- 明确每个后续批次的目标、非目标、负责人、输入依赖和验收证据。

### 主要交付物

- `docs/v1.2-scope-and-baseline.md`
- V1.2 基线采集脚本及运行说明。
- 机器可读的基线报告结构。
- V1.2 目标矩阵和明确非目标清单。
- 当前功能缺陷与一般优化项的分离清单。

### 完成标准

- 一条命令能够生成基线报告。
- 六类主线均有当前状态、已知缺口和验证方式。
- 多 Worker 状态问题和交付地基问题被明确标记为前置项。
- 后续九批范围可审阅，不存在“先实现再决定目标”的倒置。

### 本批不做

- 不直接开始大规模性能重构。
- 不决定最终 Rust 组件实现。
- 不扩充真实 Provider 或前端能力。

## 第 2 批：多 Worker 执行状态一致性

### 目标

修复生产多 Worker 下会话、LLM 线程、人格缓存和清理操作可能落入不同进程、造成上下文丢失或状态分叉的问题。

### 主要工作

- 为会话、短期对话线程和 LangGraph checkpointer 选择共享存储方案，优先复用 Redis 或项目已有共享基础设施。
- 外置 persona/runtime 与 thread/user/session 的必要映射，避免状态仅保存在 Python 单例或模块级字典中。
- 明确 `user_id`、`session_id`、`thread_id`、`call_id`、`turn_id` 和 `request_id` 的关系。
- 统一跨进程清理语义：会话关闭、用户 Memory 清空、Realtime call 结束和缓存失效应对所有 Worker 生效。
- 为共享状态定义 key 前缀、schema version、TTL、最大大小、序列化格式和升级兼容策略。
- 规定共享存储不可用时各能力的 fail-open/fail-closed 行为，禁止静默回退导致不同 Worker 持有不同会话真相。
- 增加多 Worker Contract/smoke：同一用户连续请求由不同 Worker 处理时，上下文仍保持一致。
- 增加迁移开关和回滚方式，允许在异常时退回明确的单 Worker 模式。

### 主要交付物

- `docs/operations/v1.2-execution-state-and-gates.md` 中的执行状态部分。
- 共享状态 schema 和 key 约定。
- 多 Worker 一致性测试和 smoke 指令。
- 迁移、回滚和共享存储故障说明。

### 完成标准

- 生产默认 Worker 并发下，同一 session 的多轮上下文连续率为 100%。
- 清理或关闭操作在所有 Worker 上生效。
- 状态存储不可用时返回符合约定的错误或降级 metadata，不发生静默分叉。
- 单 Worker Mock 模式仍可稳定运行。

### 本批不做

- 不重写完整 Runtime。
- 不做与执行状态无关的性能缓存。
- 不引入新的前端 session 协议。

## 第 3 批：CI、依赖与容器地基

### 目标

建立后续批次统一使用的自动化门禁，固定依赖与运行时，使 V1.2 的质量、安全和可靠性变化可以重复验证。

### 主要工作

- 建立最小 CI 流水线：静态检查、单元测试、API Contract、Mock smoke、配置一致性和仓库卫生检查。
- 将测试分成每次提交、计划任务和手动真实 Provider 三层，避免重依赖下载阻塞常规门禁。
- 确定 Python 依赖唯一真源，明确 `pyproject.toml`、`requirements.txt`、`requirements-cloud.txt` 与锁文件的关系。
- 增加依赖漂移检查，防止声明文件和锁文件不一致。
- 对齐本地、CI 和生产镜像的 Python 版本，无法对齐时记录理由和兼容测试。
- 生产容器使用非 root 用户，限制可写目录，不包含测试资产、模型缓存、Secret 和不需要的开发工具。
- 固化常用测试入口，避免每个批次自行拼接不同命令。

### 主要交付物

- CI 流水线配置。
- 依赖锁文件和依赖维护说明。
- 容器运行用户、写目录和 Python 版本说明。
- 本地与 CI 的统一验证命令。

### 完成标准

- CI 可从干净环境重复执行，并在失败时定位到具体层级。
- 核心单元测试、API Contract 和 Mock smoke 是合并必过项。
- Python 依赖存在唯一真源和漂移检查。
- 生产镜像以非 root 用户运行。
- 本地、CI、镜像的解释器版本已经对齐或有书面差异结论。

### 本批不做

- 不要求真实大模型评测进入每次提交流水线。
- 不追求一次性接入所有扫描器。
- 不将 CI 扩展成新的运维平台。

## 第 4 批：Agent 质量评测闭环

### 目标

让 RAG、Memory、Vision、Persona 和主聊天的质量变化可以用后端评测发现、定位和比较，而不是只靠人工体验。

### 主要工作

- 扩展 RAG 测试集，覆盖别名、事实问题、无答案、易混淆和低相关检索。
- 同时记录检索级和答案级指标，区分“召回了正确内容”和“最终回答被内容充分支撑”。
- 为 Memory 建立写入、过滤、去重、冲突、置顶、禁用、删除和错误记忆影响回答的回归样例。
- 为 Vision 建立角色图、日常图、文档/截图、非角色图和低置信度样例。
- 为 Persona 和主聊天建立小型行为集，覆盖角色一致性、知识问答、情绪支持、拒答和能力降级。
- 固定评测数据版本、随机性参数、结果结构和失败样例归档方式。
- 将稳定、离线、低成本的评测接入 CI；真实 Provider 评测采用固定命令和独立报告。

### 主要交付物

- `docs/quality/v1.2-agent-evaluation.md`
- 扩展后的评测 fixture。
- 统一质量报告 schema。
- 离线门禁和真实 Provider 评测指令。

### 完成标准

- RAG、Memory、Vision、Persona/主聊天均有可重复评测入口。
- 至少一个检索级指标和一个答案级指标进入常规门禁。
- 评测失败能够归因到检索、策略、上下文、生成或降级环节。
- Mock 通过不会被描述成真实模型质量通过。

### 本批不做

- 不为了提高单一分数引入复杂模型评审平台。
- 不使用真实用户对话作为默认评测集。
- 不开发前端评测页面。

## 第 5 批：Runtime/Graph 性能、成本与容量

### 目标

以基准数据定位主要后端瓶颈，并完成至少一项能够证明收益且不破坏质量的优化。

### 主要工作

- 测量冷启动、稳态、并发和可选能力关闭场景的端到端延迟。
- 报告 P50、P95、错误率、超时率、样本数、硬件和 Provider 环境。
- 使用 Graph metadata 定位 LLM、RAG、Memory、Vision、TTS、Live2D 和 response packet 阶段热点。
- 检查重复 embedding、重复检索、重复 Provider 初始化、同步 I/O 阻塞和上下文过度构造。
- 记录 LLM Token、Embedding/视觉调用次数、音频时长或其它可获得的成本代理指标。
- 定义请求总 deadline、分阶段 timeout、最大重试、并发上限和输入/输出预算。
- 只有在隐私、用户隔离和失效语义清楚时才引入缓存。
- 对优化前后运行质量、Contract 和故障回归。

### 主要交付物

- 性能与成本基准脚本。
- 基准报告和容量假设。
- 阶段预算与超时表。
- 至少一项热点优化及前后对照，或“不值得优化”的证据报告。

### 完成标准

- 主要耗时和资源热点由数据而非直觉确认。
- 至少一项优化具有可重复的量化收益。
- 优化没有造成 Contract、质量、隐私或故障行为退化。
- Provider 重试和总 deadline 不会形成无上限等待或级联重试。

### 本批不做

- 不只凭局部 microbenchmark 决定架构。
- 不为缓存命中率牺牲用户隔离或数据新鲜度。
- 不把 Rust 用作普通性能重写语言。

## 第 6 批：威胁模型与安全目标选择

### 目标

确定 V1.2 实际要解决的一至两个安全目标，形成可审阅的威胁、范围、控制和验证计划；安全方向必须在本批结束时收口，不能长期停留在候选列表。

### 主要工作

- 绘制 API、Runtime/Graph、Provider、数据库、对象存储、Redis、Worker 和部署入口的数据流与信任边界。
- 盘点 Secret、用户文本、图片、音频、长期记忆、任务和生成内容等资产。
- 明确 `user_id`、session、call、task、memory、object key 等资源的可信来源和所有权关系。
- 按 STRIDE 或同等方法分析越权、伪造、篡改、泄漏、拒绝服务和权限提升。
- 评估身份授权、上传解析、隐私/Secret、供应链及 Prompt/检索内容信任边界等候选方向。
- 按影响、暴露面、控制缺口、可验证程度和实施成本排序。
- 选定一至两个 V1.2 安全目标，同时列出本版本不做的安全事项和原因。
- 初步评估目标是否适合 Rust，形成 ADR 决策输入。

### 主要交付物

- `docs/security/threat-model-v1.2.md`
- 安全资产、信任边界和风险登记表。
- 本版本选定安全目标清单。
- 本版本不做的安全事项及风险接受说明。
- Rust 候选问题和决策门槛。

### 完成标准

- 所有 P0/P1 风险都有负责人、验证方法和处理决定。
- 安全实现范围被限制在一至两个主题。
- 未选目标不会自动膨胀为本版本必做项。
- Rust 选型由安全问题驱动，而不是由语言偏好倒推。

### 本批不做

- 不直接实现未经选择的全部安全候选。
- 不承诺全面解决 Prompt Injection。
- 不自研密码算法、认证协议或加密格式。

## 第 7 批：选定安全目标落地

### 目标

实现第 6 批选定的一至两个安全主题，并用负向测试证明安全控制确实阻止了目标威胁。

### 主要工作

根据第 6 批结论选择有限子集，不能默认把下面三类全部纳入：

- **身份与资源所有权**：可信认证主体、跨用户 Memory/文件/call/task 隔离、管理面和用户面分离。
- **上传与解析安全**：请求体和文件大小、允许格式、扩展名/MIME/魔数一致性、路径规范化、解析资源上限和异常样本。
- **Secret、日志与隐私**：配置快照脱敏、canary Secret 扫描、日志策略、数据保留与删除、CORS/代理/TLS 配置检查。

共同要求：

- API 错误使用稳定 `stage`，不暴露内部路径、Secret 或完整用户内容。
- 每个安全控制至少有一个正常测试和一个恶意/越权负向测试。
- 生产配置采用 fail-closed 的安全入口不得静默绕过。
- 更新配置模板、安全文档和运维检查。

### 主要交付物

- 选定安全控制的实现和配置。
- API Contract、单元测试和恶意样例 fixture。
- 安全回归指令和预期结果。
- 数据/Secret 处理或事件响应文档更新。

### 完成标准

- 选定威胁有自动化测试证明已缓解。
- 越权、畸形输入或 canary Secret 不会穿透目标边界。
- 未选安全方向保持明确的风险登记，不产生无边界扩展。
- 现有文本聊天和 Mock 主链路仍可运行。

### 本批不做

- 不扩大到完整身份平台或通用零信任系统。
- 不在一个批次同时重写认证、上传、日志和供应链。
- 不把模型输出作为授权依据。

## 第 8 批：Rust 安全组件决策与条件原型

### 目标

根据第 6、7 批结果决定 Rust 是否适合承担某个确定性安全边界。采用 Rust 时交付小型可验证原型；不采用时交付同等有效的 ADR，而不是为了满足语言目标制造组件。

### 主要工作

- 比较 Python 实现、成熟现成工具、Rust library/Python binding、Rust CLI/stdio 和独立服务的风险与成本。
- 只有边界明确时才实现，例如文件魔数/MIME 预检、确定性 Secret 扫描或制品摘要验证。
- 定义版本化输入输出 schema、最大输入、超时、错误码和失败策略。
- 默认禁止 `unsafe`；确需使用时逐处说明并测试。
- 使用成熟库实现 Hash/签名/解析，不自创密码学。
- 增加 Rust 单测、模糊/边界测试及 Python Contract 测试。
- 验证 panic、超时、非零退出、版本不匹配和空输出不会使 Python API 崩溃。
- 对比安全收益、性能、构建复杂度和维护成本，决定保留、暂缓或弃用。

### 主要交付物

- `docs/adr/ADR-00XX-rust-security-component.md`
- 若采用：Rust crate、`Cargo.lock`、测试、构建命令和 Python 集成 Contract。
- 若不采用：明确的不采用原因、替代控制和未来重新评估条件。
- Rust 组件故障与回滚说明。

### 完成标准

- Rust 决策有证据支持。
- 若采用，组件只处理窄边界输入，接口版本化且资源有上限。
- Python 集成在组件失败时行为明确，不泄漏 stderr、路径或用户内容。
- 若收益不足，允许以“不采用 Rust”完成本批。

### 本批不做

- 不将 Rust 扩展为新的通用后端框架。
- 不重写 FastAPI、Graph、RAG、Memory 或 Realtime。
- 不仅因 Rust 内存安全就假设第三方解析器和业务逻辑绝对安全。

## 第 9 批：Cloud/Worker 故障恢复与数据生命周期

### 目标

验证 Redis、任务队列、Worker、对象存储和 Provider 故障时的隔离、重试和恢复行为，并统一运行数据的保留与删除规则。

### 主要工作

- 为 Redis、对象存储、LLM、ASR、TTS 和任务队列建立故障矩阵，明确 fail-open/fail-closed。
- 为任务定义幂等键、重复投递、副作用、最大 attempts、总 deadline、退避、取消、stale recovery 和 dead-letter 重放。
- 注入 Redis 断连、对象存储 5xx、Provider 超时、Worker 中止、重复任务等故障。
- 验证 Realtime 与会话状态在 Redis 故障时不会多实例静默分叉。
- 明确 Memory、上传对象、缓存、task/call 状态、死信、日志和备份的 TTL 与删除责任。
- 验证删除在主存储、派生缓存、备份和测试副本中的边界。
- 分离 liveness 和 readiness，避免可选能力短暂故障造成容器无意义重启。
- 增加恢复 runbook 和人工重放边界。

### 主要交付物

- `docs/operations/v1.2-reliability-and-data-lifecycle.md`
- 依赖故障矩阵和故障注入测试。
- 任务幂等、重试、死信及重放规则。
- 数据保留、删除和备份边界表。
- 运维恢复与排障指令。

### 完成标准

- 单个可选依赖失败不会无界扩散到整个聊天主链路。
- 重试有总上限，不产生不可控重复副作用。
- 任务、call 和用户数据的 TTL/删除规则有测试或可审计证据。
- readiness 能阻止不适合接流量的实例，liveness 不被可选依赖误伤。

### 本批不做

- 不建设新的通用调度平台。
- 不承诺所有外部 Provider 都达到完全相同的恢复能力。
- 不通过无限重试掩盖依赖故障。

## 四、批次依赖关系

批次默认按以下顺序执行：

```text
第 1 批 基线与范围
  -> 第 2 批 多 Worker 状态一致性
  -> 第 3 批 CI/依赖/容器地基
  -> 第 4 批 Agent 质量
  -> 第 5 批 性能与成本
  -> 第 6 批 安全选题
  -> 第 7 批 安全落地
  -> 第 8 批 Rust 条件原型
  -> 第 9 批 Cloud/数据可靠性
  -> 第 10 批 发布收尾
```

允许的调整：

- 第 4 批和第 5 批在第 3 批完成后可以交换顺序。
- 第 6 批可在第 4、5 批期间提前准备，但必须在第 7、8 批之前完成审阅。
- 第 8 批如果 ADR 结论为不采用 Rust，可以较快结束，但不能跳过决策记录。
- 第 9 批可以复用第 2 批的共享状态故障测试，但不能重复建设状态存储。

不允许的调整：

- 第 2 批不得被删除或推迟到第 10 批。
- 第 3 批未完成前，不把后续评测和安全测试视为稳定门禁。
- 第 7 批不得在第 6 批选题前扩大实现范围。
- 第 8 批不得为了使用 Rust 而脱离安全目标单独立项。
- 第 10 批不得接收新的功能性需求。

## 五、V1.2 整体完成定义

V1.2 后端版本完成时，应同时满足：

- 多 Worker 下会话、LLM 线程、persona、Memory 清理和 Realtime 状态不会静默分叉。
- 存在合并必过的 CI 门禁、依赖唯一真源、锁文件和非 root 生产镜像。
- RAG、Memory、Vision、Persona/主聊天有版本化评测和失败回归。
- 关键 Runtime/Graph 路径有性能、成本和容量基线，并完成有证据的优化决策。
- V1.2 安全目标已经从威胁模型中选定并完成有限落地。
- Rust 安全组件有明确的采用或不采用结论；若采用，具备稳定 Contract 和故障边界。
- Cloud/Worker 故障恢复、幂等、重试、死信和数据生命周期经过验证。
- 发布产物通过依赖、Secret、配置、镜像、测试、评测和文档检查。
- 已知风险有负责人、优先级、缓解措施和截止时间。
- Flutter、Qt、Web UI 和其它前端工作仍不属于本版本完成条件。
